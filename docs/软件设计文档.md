# Base Augment Agent 软件设计文档

> 本文档基于 `src/agent/` 当前实现编写，覆盖系统概览、架构、模块职责、核心数据流、线程/并发模型、资源管理、错误处理、配置体系与扩展点。

## 1. 系统概览

### 1.1 定位

Base Augment Agent 是一个**本地自主 Agent**：

- **本地优先**：所有工具执行、文件操作、知识库向量检索都在本地完成；唯一的外部网络依赖是 LLM API（OpenAI 兼容）。
- **图形界面**：基于 PyQt6 的桌面应用，提供对话、思考过程、日志三栏式交互体验。
- **可插拔工具**：21 个内置工具（原子 8 + 能力 12 + 1 个条件注册；另有 2 个原子命名别名，`webexec_js` / `web_execute_js` 仅在配置浏览器端点时注册）+ MCP 协议接入远程工具，工具以「类 + schema」形式注册，由模型自主调用。
- **本地 RAG 知识库**：自动解析文档、清洗、切片、向量化、LanceDB 存储、BGE 重排序，全程离线。
- **内核控制流**：三态自动机（THINK / ACT / CONSOLIDATE）+ 五级信息压缩（L0–L4），上下文硬性控制在 30k 以内。内核**只控制流**——历史在 `Session`、能力在 `code_run`/`shell_run`、经验在 `memory`/`skills`，三者都是注入物。

### 1.2 技术栈

| 层 | 技术 |
|----|------|
| UI | PyQt6（QMainWindow / QThread / pyqtSignal） |
| LLM 传输 | httpx（流式 SSE） |
| 工具系统 | 自研 `Tool` 抽象 + MCP JSON-RPC over stdio |
| 向量存储 | LanceDB（本地 Lance 列式格式） |
| 嵌入模型 | FastEmbed (ONNX Runtime) — `nomic-ai/nomic-embed-text-v1.5-Q`（Q4 量化，~137MB） |
| 重排序 | FastEmbed TextCrossEncoder (ONNX Runtime) — `BAAI/bge-reranker-v2-m3-int8`（INT8 量化，~570MB；fp32 全量 2.27GB） |
| 文档解析 | python-docx / openpyxl / python-pptx / PyMuPDF / ebooklib / bs4 / RapidOCR |
| 持久化 | JSON 文件（config / memory / graph / skills / manifest）+ LanceDB（向量索引） |

### 1.3 入口

[main.py](file:///Users/arlenecc/codebase/base-agent/main.py) 将 `src/` 注入 `sys.path`，调用 [agent.ui.main_window.run()](file:///Users/arlenecc/codebase/base-agent/src/agent/ui/main_window.py)，后者构建 `QApplication` + `MainWindow` 进入 Qt 事件循环。

### 2.2 关键设计原则

1. **UI 线程绝不阻塞**：所有耗时操作（LLM 流式调用、RAG ingest、依赖安装、模型列表获取）都在 QThread 中执行；UI 通过 `pyqtSignal` 接收事件。
2. **回调驱动的协议**：Agent 通过 `AgentCallbacks` 抽象与外界通信，UI 层用 `Bridge` 把回调转成 Qt 信号，实现线程安全。
3. **资源显式释放**：ONNX Runtime / LanceDB / MCP 子进程 / httpx 连接都通过 `close()` / `shutdown()` 显式释放，不依赖 Python GC。
4. **协作式取消**：所有长任务都有取消标志（`threading.Event`），在文件/批处理边界检查后退出，不强制 kill。
5. **原子写**：所有 JSON 持久化（config / memory / skills / manifest / memory.md / 文件写入）都使用 temp + `os.replace()` 原子写。
6. **工作区沙箱**：文件工具用 `realpath` 解析并前缀检查，符号链接逃逸也被拒绝；`code_run` 通过 `builtins.open` 守卫拦截工作区外的写操作。

## 3. 模块职责详解

### 3.0 [src/agent/kernel/](file:///Users/arlenecc/codebase/base-agent/src/agent/kernel) — 内核（只控制流）

内核是本轮重构新增的核心层。设计原则：**内核只控制流**，历史 / 能力 / 经验全部是注入物。

```
                    ┌───────────────────────────────┐
                    │                               │
   ┌────────────┐   │ tool_calls   ┌────────────┐   │
   │   THINK    │───┼─────────────►│    ACT     │   │
   │  (决策态)   │   │              │  (执行态)   │   │
   └─────┬──────┘   │              └──────┬─────┘   │
         │          │                     │         │
         │ 无 tool  │                     │ 预算告罄 │
         │          │                     │ / 每 N 轮│
         ▼          │              ┌──────▼────────┐│
   ┌────────────┐   │              │  CONSOLIDATE  ││
   │   EXIT     │◄──┴──────────────│   (沉淀态)     ││
   │  (终止态)   │   压缩完成 → THINK └───────────────┘│
   └────────────┘                                    │
                                                     │
    ◄────────────────────────────────────────────────┘
```

**转移表**（`outcome.next_state`）：

| 当前态 | 事件 | 下一态 |
|---|---|---|
| THINK | `has_calls` | ACT |
| THINK | `no_calls` | EXIT |
| ACT | `consolidate` | CONSOLIDATE |
| ACT | `interrupt`（ask_user / 取消 / 错误） | EXIT |
| CONSOLIDATE | 压缩完成 | THINK |
| 任意 | 未知组合 | EXIT（绝不停在未知态） |

终止原因 `ExitReason`：`DONE` / `INTERRUPT` / `MAX_TURNS` / `CANCELLED` / `ERROR`。

#### 3.0.1 [outcome.py](file:///Users/arlenecc/codebase/base-agent/src/agent/kernel/outcome.py)

`KernelState` / `ExitReason` / `ToolCall` / `StepOutcome` / `LLMResponse` / `TurnRecord` 与转移表。

`StepOutcome(data, next_prompt, should_exit)` 是整个控制流的枢纽——**`next_prompt` 为空即终止**，因此业务代码只需回答「下一步给模型什么」，不需要知道循环怎么走。

#### 3.0.2 [budget.py](file:///Users/arlenecc/codebase/base-agent/src/agent/kernel/budget.py) — 30k 预算

配额按比例从 `total` 派生（换模型窗口时无需改代码）：

| 区 | 比例 | 30k 时 | 内容 |
|---|---|---|---|
| `system` | 13% | 3.9k | 系统提示 + 记忆索引 + 工作记忆 checkpoint |
| `earlier` | 9% | 2.7k | L3 折叠摘要区 |
| `raw` | 40% | 12k | 最近 K 轮原文（含 L1 裁剪后的工具输出） |
| `tools` | 17% | 5.1k | 工具 schema |
| `reserve` | 21% | 6.3k | 模型输出 + 估算误差 |

**超支转嫁**：`system` / `tools` 用超的部分从 `raw` 额度里扣——否则 30k 只是记账，不真正约束。
`remaining_for_tool(n, max_chars)` 按「RAW 余额 ÷ 并发调用数」分配单条工具输出上限，**并发 4 个工具时每个自动只拿 1/4**，工具代码无需感知。

#### 3.0.3 [compressor.py](file:///Users/arlenecc/codebase/base-agent/src/agent/kernel/compressor.py) — L0–L4

| 级 | 函数 | 时机 | 手段 | 上限 |
|---|---|---|---|---|
| L0 | `l0_capture` | 工具返回瞬间 | 硬上限 head+tail | 单条 ≤ 20K 字符 |
| L1 | `l1_trim` / `l1_trim_result` | 注入本轮前 | 按 RAW 余额分配 `maxlen`，去噪（脚本/style/控制字符） | 单条 ≤ 6K 字符 |
| L2 | `l2_summary` | 每轮结束 | 优先 `<summary>`，回退首句/工具名；**永不返回空串** | ≤ 30 字 |
| L3 | `l3_fold` | 预算告罄 / 每 N 轮 | 旧轮 → 一行摘要；连续相同动作塌缩为 `（N turns）` | ≤ 40 行 |
| L4 | `l4_extract_json` / `l4_normalize` | 任务完成 / 检查点 | 蒸馏出 facts / lessons / skill；输出类型确定，脏输入不抛 | — |

#### 3.0.4 [session.py](file:///Users/arlenecc/codebase/base-agent/src/agent/kernel/session.py) — 历史托管

**Session 是历史的唯一所有者**，`Agent._history` 只剩兼容字段。

- `TurnRecord`：一轮的物理快照（`prompt` / `assistant_text` / `tool_calls` / `tool_results` / `summary`）。`summary` 由 L2 在 `finish_turn` 时生成并**不可变**——历史一旦沉淀就不再被重写。
- `_windows()`（L3 核心）：把 turns 切成 `(old, raw)`。`raw` = 最近 `raw_turns` 个**已完成**轮 + 当前进行中的轮；`old` 全部折叠成一行摘要。预算紧张时自动收缩 `raw`（这就是折叠的自动触发点）。
- `force_fold(n)`：把最旧的 n 轮从 `turns` 移入 `extra_digest`。
- `anchor_prompt()`：下一轮 user 消息的正文——只回注折叠历史 + `key_info` + 一次性提示（如「上一轮被截断」），历史不重发。
- `set_key_info()`：L4 的工作记忆 checkpoint，每轮由 `update_working_checkpoint` 工具写入。

**关键不变量**：折叠以「整轮」为单位，因此**结构上不可能**产生悬挂 `tool` 消息（旧实现靠事后修复边界）。

#### 3.0.5 [loop.py](file:///Users/arlenecc/codebase/base-agent/src/agent/kernel/loop.py) — KernelLoop

```
run(user_input) → KernelResult(reason, turns, turns_used, error)
  while turns_used < max_turns:              # 每次 run() 独立计数
      state = THINK
      messages = session.build_messages(system_prompt(), anchor)
      resp = llm.chat_stream(messages, tools)
      ├─ 空回复 → 重试（≤3 次）后按 DONE 收尾
      ├─ 只吐代码块无 tool_call → reask 一次，再犯则收尾（防死循环）
      ├─ 上下文超长 → 分类为 non-fatal，转 CONSOLIDATE 兜底
      ├─ 无 tool_calls → finish_turn → EXIT(DONE)
      └─ 有 tool_calls → state = ACT
  ACT: 并发/串行分发 → outcomes
      ├─ ask_user → EXIT(INTERRUPT)
      ├─ 取消 / 致命错误 → EXIT(CANCELLED/ERROR)
      └─ 其余 → finish_turn → CONSOLIDATE
  CONSOLIDATE: 预算告罄或每 N 轮 → force_fold → 回 THINK
```

`max_turns` 是**本次 `run()` 的轮次上限**，不是会话累计（早期实现用累计值，导致累计 15 轮后 Agent 彻底不再调 LLM）。
`llm` 允许传入 callable，UI 整体替换 `agent.llm` 后内核仍能拿到最新客户端。

### 3.1 [src/agent/agent.py](file:///Users/arlenecc/codebase/base-agent/src/agent/agent.py) — Agent 门面

**职责**：保留 callbacks / skills / 配置 / 事实抽取 / 记忆写入，**把控制流委托给内核**。自身不再持有历史与循环。

**关键组件**：
- `AgentCallbacks`：定义所有 UI 钩子（`on_content` / `on_reasoning` / `on_tool_start/end` / `on_log` / `on_usage` / `on_token_speed` / `on_skill_suggested` / `on_error` / `on_context_shrunk` / `confirm` / `ask_user` / `on_finished`）。内核只依赖这个抽象，不认识 UI。
- `SYSTEM_PROMPT`：精简的固化系统提示（~200 tok）。
- `_AgentKernelHooks`：内核三态钩子。内核不认识"经验"，L4 蒸馏 / 事实抽取 / 技能建议都由这个适配器在 `finished` 时落地。
- `_ToolDispatcher`：内核不认识"能力"，工具发现 / 确认 / 并行策略都在这里，`ToolRegistry` 是它的能力来源。
- `Agent.run()` → `KernelLoop.run()`。旧的单体循环已移除，旧的 `_shrink_context` 降级为 `_shrink_session` 兜底（仅在 L3 折叠用尽时触发）。

**配置参数**：
- `max_iterations`（默认 15）：内核的 `max_turns`，**每次 run() 独立计数**。
- `kernel_max_context_tokens` / `kernel_raw_turns` / `kernel_consolidate_every` / `kernel_max_tool_chars` / `kernel_max_digest_lines`：见 §8.1。
- `max_history` / `max_context_tokens` / `context_shrink_ratio`：仅为兼容旧配置保留，已不参与决策。

### 3.2 [src/agent/llm_client.py](file:///Users/arlenecc/codebase/base-agent/src/agent/llm_client.py) — LLM 流式客户端

**职责**：通过 OpenAI 兼容 API 进行流式 chat completions。

**关键设计**：
- 单一 `httpx.Client` 实例（连接池复用）。
- **结构化超时**：`httpx.Timeout(connect=timeout, read=max(timeout,60), write=timeout, pool=timeout)`——`read` 是流式响应**每个 chunk 之间的最大间隔**。纯 `timeout=float` 只约束整请求（流式下首字节到达后即失效），本地模型生成中途卡住会让 `iter_lines()` **无限阻塞**（表现为「回复到一半停住不动」）；设置 read 超时后最多等 60s 就抛 `httpx.ReadTimeout` 而非永久卡死。
- `chat_stream`（[L88-166](file:///Users/arlenecc/codebase/base-agent/src/agent/llm_client.py#L88-L166)）：
  - 解析 SSE `data:` 行，跳过 `[DONE]`。
  - 累积 `delta.tool_calls`（按 `index` 分桶拼接 `function.name` / `function.arguments`）。
  - 支持 DeepSeek 风格的 `reasoning_content` 字段。
  - 末尾发射 `StreamEvent(type="done", tool_calls=..., usage=...)`，其中 `usage` 来自 `stream_options.include_usage=True`。
- 透传 `min_p` / `top_k` / `repetition_penalty` 等本地模型常用参数。

### 3.3 [src/agent/tools/](file:///Users/arlenecc/codebase/base-agent/src/agent/tools) — 工具系统

#### 3.3.1 [base.py](file:///Users/arlenecc/codebase/base-agent/src/agent/tools/base.py) — 注册中心

**`Tool` 抽象**（[L29-58](file:///Users/arlenecc/codebase/base-agent/src/agent/tools/base.py#L29-L58)）：
- `name` / `description` / `parameters`（JSON Schema） / `destructive`（是否需要确认）。
- `should_confirm(args)`：默认 `return self.destructive`，可重写实现细粒度策略。
- `schema()`：转为 OpenAI function-calling 格式。

**确认消息（`Agent._confirm_message`）**：`code_run`/`shell_run` 的确认弹窗**只显示用途说明，不贴代码/命令全文**（避免超长文本把 Yes/No 按钮顶出屏幕）：
- **启发式优先（零延迟）**：代码提取顶部注释/docstring/函数名/包安装命令；命令走内置映射（pip/npm/git/rm/docker 等）→ 人类可读用途（`_summarize_code` / `_summarize_command` / `_looks_like_command`）。绝大多数模型生成的代码带注释，走此路径即时返回。
- **LLM 兜底**：仅当启发式得到泛化描述（如「执行代码片段：xxx」、未知命令）时，`_describe_code_purpose` 才用独立抽取客户端生成 ≤20 字中文用途——避免每次确认都同步阻塞 1-3s。
- UI 兜底：`_on_confirm_request` 对消息截断到 800 字符。

**`ToolRegistry`**（[L61-233](file:///Users/arlenecc/codebase/base-agent/src/agent/tools/base.py#L61-L233)）：
- `__init__` 中 `_register_defaults()` 注册 12 个默认内置工具（含 3 个 memory 工具、2 个 skill 工具）+ RAG 工具 + MCP 工具；`webexec_js` 仅在 `browser_endpoint` 配置时注册（省 ~146 tok schema）。
- `reload_rag()`：同步完成后刷新 agent 的 LanceDB 表句柄。
- `shutdown()`：停止所有 MCP 子进程，释放 RAGEngine 资源、LongTermMemory 单例与 SkillIndex 单例。
- `execute(name, args)`：捕获 `TypeError`（参数不匹配）和未预期异常，统一返回 `ToolResult`。

**`parse_args`**（[L236-251](file:///Users/arlenecc/codebase/base-agent/src/agent/tools/base.py#L236-L251)）：解析 JSON 参数；空串返回 `{}`，非空但非法 JSON 抛 `ValueError`（让模型看到错误而非被当作 `{}` 误诊）。

**向量索引**（懒初始化 + 双重检查锁）：

- **锁外批量索引**：`create_entity` / `add_observations` 在锁内收集 `to_index` 列表，释放 `_lock` 后调用 `_index_observations_batch()`——用 `embed_documents()` 将整批观察在**单次 ONNX 前向**中完成嵌入（替代逐条 `embed_query()`，N 条观察从 N×10-50ms 降为一次批量计算），避免 ONNX 计算阻塞 JSON 读取。

- 观察 upsert：用 `entity|observation` 的 md5 hash 做主键，先 delete 再 add。
- 删实体时 `_deindex_observations()` 批量删除该实体所有向量；实体名的单引号做 SQL 转义（`'` → `''`），防止 filter 表达式被畸形/注入（实体名来自 LLM，不可信）。

### 3.5.1 [src/agent/skill_index.py](file:///Users/arlenecc/codebase/base-agent/src/agent/skill_index.py) — 技能索引

**`SkillIndex`**：扫描 `.agent/skills/` 目录，把所有技能元数据汇总为一张 `_index.json` 索引表，供 `skill_search` 工具 O(1) 加载检索。

```
.agent/skills/
├── _index.json            ← 自动生成的索引（原子写：tmp + os.replace）
└── <skill-name>/

**关键设计**：
- **防抖扫描**（`_should_scan`）：满足任一条件才重建索引——从未扫描 / 距上次超过 `_SCAN_INTERVAL`（300s）/ 技能目录 mtime 变化。加载已有索引时同步 `_last_dir_mtime`，避免启动后立即重扫。

- **单例**：实例缓存在 `ToolRegistry._skill_index` 上（由 `skill_search` / `skill_load` 懒创建），`ToolRegistry.shutdown()` 解除引用。

### 3.5.2 [src/agent/skill_retriever.py](file:///Users/arlenecc/codebase/base-agent/src/agent/skill_retriever.py) — SKILL.md 混合检索

对 `workspace/skills` 下的 **SKILL.md** 文件做语义 + 全文混合检索，供 `skill_semantic_search` 工具使用。

**扫描与解析**：
- `SkillScanner`：递归 `os.walk` 扫描所有 SKILL.md，跳过 `tests/`/`test/`/`__pycache__`/隐藏目录；防抖扫描（目录 mtime 变化或 300s 间隔）。
- `parse_skill_md`：解析 YAML frontmatter（手写轻量解析，不依赖 PyYAML）——`name`/`description`/`tags`（支持 `[a, b]` 流式数组与逗号分隔）；解析正文段落——`## When to Use This Skill`（适用）、`## When NOT to Use`（不适用）、`## Examples`（示例）。

**向量化与建表**（`SkillVectorStore`）：
- 用共享的 nomic-embed-text 分别对 `description` 与 `examples`（无 examples 时回退 when_to_use/description）计算向量，批量两次前向。
- LanceDB 表 `skills` 列：`dir`（SKILL.md 所在目录）、`name`、`tags`、`description`、`desc_vec`（description 向量）、`examples_vec`（examples 向量）、`combined`（name+tags+description+examples 拼接原文）、`combined_fts`（jieba 预分词，供 BM25）。
- 显式 pyarrow schema 声明向量列为 `list(float32)`，避免 LanceDB 把 `list[float]` 误推断为标量 Float64。
- 向量归一化后入库，用 L2 距离模拟余弦相似度（`1 - d²/2`）。
- **小批次构建（防内存爆炸）**：`build()` 以 `batch_size=8` 分批 embed + `table.add()`，每批完成后释放；`description`/`examples`/`combined` 分别截断至 2000/3000/6000 字符（SKILL.md 的 Examples 段落可达数十 KB，整段 embed + 分词会放大内存与耗时）。实测 2757 个 skill 全量索引：峰值 RSS **4.19 GB**、耗时 12.4 分钟；此前一次性处理全部文本时峰值达 65 GB 导致系统卡死。

**混合检索**（`SkillRetriever.retrieve`）：
1. 向量检索：分别对 `desc_vec`、`examples_vec` 检索，两通道按 **0.6:0.4** 加权融合（同一技能两通道都命中时，相似度按比例融合成一个分数）；取 3 候选。
2. BM25 全文检索 `combined_fts`：取 3 候选。
3. 去重（按 `dir`）；向量分数为统一排序依据（BM25 命中的技能若未在向量候选中，补查其向量相似度作为 score）。
4. 剔除相似度 < 0.5 的候选。
5. 返回候选的 name+tags+description，由 agent（大模型）判断选用哪个，再 `skill_load` 读取 SKILL.md 及目录下 references/scripts 支持文件。

**资源管理**：`SkillRetriever` 单例挂在 `ToolRegistry._skill_retriever`，`shutdown()` 关闭 LanceDB 连接（不关闭共享的 embedding 单例）。

Markdown 文本
  ├─ _split_by_structure()：按 #~###### 标题 + 空行段落边界切分
  ├─ 超长章节（>800 tokens）→ semantic_chunk_text()（chonkie 语义细分）
  ├─ _merge_to_target_size()：合并过小块至 ≥100 tokens
  └─ _apply_overlap()：相邻块 10% overlap（句子边界对齐）
```

- **语义分块**（`semantic_chunker`）：chonkie `SemanticChunker` + `threshold=0.7` 按语义相似度切分；CJK 分隔符（`。！？；，`）避免整段中文当一句。
- **嵌入复用**：`_ChonkieEmbeddingAdapter` 继承 chonkie `BaseEmbeddings`，包装进程级 nomic-embed-text 单例——语义分块与向量存储**共用同一份 ~137MB ONNX 模型**，不重复加载。
- **overlap 句子对齐**（`_tail_by_tokens`）：按句子边界倒序取尾部，绝不切断句子。
- **三级回退**：chonkie 未安装 → 语义分块返回 `None` → 递归分块兜底，任何环境都能工作。

#### 3.6.6 [vector_store.py](file:///Users/arlenecc/codebase/base-agent/src/agent/rag/vector_store.py) — 向量存储

**`FastEmbedEmbeddingFunction`**：
- `nomic-ai/nomic-embed-text-v1.5` via ONNX Runtime，~130MB 量化后，离线可用。
- **文档/查询前缀**：`search_document: ` / `search_query: `（nomic 模型要求）。
- `embed_documents(texts)`：批量文档嵌入——整批文本在**单次 ONNX 前向**中完成，远快于逐条 `embed_query()`；RAG 切片入库与知识图谱观察批量索引共用此路径。
- 懒加载，首次调用才下载模型。

**`VectorStore`**（[L76-660](file:///Users/arlenecc/codebase/base-agent/src/agent/rag/vector_store.py#L76-L660)）：
- **存储列**：每切片存入 `vector`（nomic-embed-text 向量）、`text`（完整原文）、`source`（来源文件名）、`chunk_index`（切片编号）、`text_fts`（jieba 预分词，BM25 索引列）。
- **BM25 全文索引**（`_ensure_fts_index` + `_tokenize_for_fts`）：`text_fts` 列用 jieba 分词后空格连接，原生 FTS `simple` tokenizer 索引。采用 Python 层 jieba 预分词 + simple 索引的业界标准做法（规避中文无空格无法分词）。索引在每次 add 后 `replace=True` 重建（LanceDB 的 FTS 索引不会自动增量更新）。`_ensure_fts_index` 兼容 lancedb 0.25（`create_fts_index(use_tantivy=False)`）与 0.37（`create_index(config=FTS)`）两种 API。
- **文档元数据表**（`_documents_table`，Meta-context RAG）：`doc_name`（文档名）/ `digest`（缩略版本：目录结构 + 章节标题）/ `markdown`（完整 Markdown）/ `chapters`（章节结构 JSON）。`upsert_document` 按 `doc_id`（文档名 md5）upsert；`get_document_digest` 支持精确/部分标题匹配；表懒创建用 `_documents_lock` 双重检查锁保护（多 worker 并发 ingest 时防 `create_table` 竞态）。documents 表内容有内存缓存（`_documents_cache`），`get_document_digest`/`list_documents` 不重复全表 `to_pylist()`；`upsert_document` 的 delete+add 与 `delete_document` 在 `_documents_lock` 下串行化，避免并发写入交错。
- **`_ensure_table()`**：每次调用都重查 `table_names()`（不缓存"表不存在"），因为 SyncKnowledgeWorker 可能已创建表。
- **`add_streaming`**（[L254-411](file:///Users/arlenecc/codebase/base-agent/src/agent/rag/vector_store.py#L254-L411)）：流式写入，内存占用 O(batch_size) 而非 O(总 chunks)。
  - 第一批特殊处理：决定是 `create_table` 还是 `add` 到已有表。
  - 已有表：按 source 的 md5 hash 用 `id LIKE '{hash}_%'` 删除旧记录（upsert 语义）。
  - 批量 20 条/批。
- **`_embed_chunks`**：将每批 20 个 chunk 再拆分为 5 条/子批进行 embedding，每个子批次完成后 `time.sleep(0.01)` 释放 GIL，让主线程的 QTimer 有机会轮询日志缓冲区并更新 UI。ONNX Runtime 的 `embed()` 在 C++ 计算期间持有 GIL，整批一次性嵌入会导致 UI 长时间冻结。
- **`search`**：向量归一化为单位长度后用 L2 距离模拟余弦相似度；`_distance` 转换为 `[0,1]` 相似度分数。
- **`search_fts`**：BM25 关键词检索（原生 FTS `simple` tokenizer + jieba 预分词），支持 `where` SQL 过滤。
- **`search_with_rerank`**：混合检索——向量 `top_k×4` + BM25 `top_k×4`（两者都应用 `where` 过滤）→ 按 (source, chunk_index) 合并去重 → FastEmbed reranker 精排 → 过滤相似度 < 0.7 → 返回 ≤ top_k。
- **`rerank`**：reranker 不可用时回退到距离排序；分数归一化到 `[0,1]`。有 reranker 时按 `min_similarity=0.7` 过滤（回退模式不强制过滤，因距离分数语义不同）。
- **`_get_reranker`**：懒加载 FastEmbed reranker（TextCrossEncoder，ONNX Runtime，与 embedding 同源，无需 torch / FlagEmbedding，在 numpy 2.x 下可用）；加载用 `_reranker_state` 状态机（idle/loading/done/failed）去重并发加载线程，超时后后台线程完成仍写回结果。
- **`_check_schema_migration`**：旧表缺少 `text_fts` 列时自动迁移——`to_arrow().to_pylist()` 读旧数据（无 pandas 依赖），drop 旧表后重建并回填 `text_fts` 列。
- **`close()`**（[L571-623](file:///Users/arlenecc/codebase/base-agent/src/agent/rag/vector_store.py#L571-L623)）：
  - 显式调用 ONNX `InferenceSession.release()` 立即回收 C++ 堆。
  - FastEmbed reranker 的 ONNX 模型在 close 时由状态机置 None 并丢弃（Python GC 回收），不再依赖 `model.cpu()`。
- **`reload()`**：丢弃表句柄，下次操作重新打开。

#### 3.6.7 [document_outline.py](file:///Users/arlenecc/codebase/base-agent/src/agent/rag/document_outline.py) — Meta-context RAG（目录结构提取）

**`document_outline`**（目录结构提取，不生成逐章摘要）：

缩略版本（digest）只包含文档的**目录结构（标题层级）**，不包含逐章摘要。逐章 LLM 摘要慢、费 token、且对本地模型易产生空结果，标题层级已足以支撑定向检索。提取策略按优先级：

2. **纯文本启发式**（`extract_chapters_plain`，无 `#` 标题时回退）：
   - **目录块识别**（`_extract_from_toc_block`）：定位 `目录`/`目 录`/`Contents`/`Table of Contents` 标记，收集其后一行一个标题的条目，遇到正文句（以句末标点结尾）终止。

   - **编号标题**（`_numbered_match`）：`1.`/`1.1`/`1.1.1`。
   - **EPUB 链接**（`_normalize_title`）：`[TITLE](#anchor)` → `TITLE`。
   - **全大写短行**（`_ALLCAPS_RE`）：英文 EPUB 章节标题，要求前后空行降低误判。
- `build_digest`：先尝试 Markdown 标题，无结果回退纯文本启发式，输出 `# 目录\n...`；`build_and_store_digest` 在完全无标题时兜底为文档名（避免空目录）。

**增量重刷**（`RAGEngine.ensure_digests_for_cached_documents(refresh_stale=True)`）：

**检索闭环**（Meta-context + Targeted RAG）：

#### 3.7.1 日志显示架构

知识同步期间的日志显示采用 **QTimer 轮询 + 线程安全日志缓冲区** 方案，而非传统的 Qt queued signal：

**两条日志通道**：
1. **QSignalLogHandler**（常态）：挂在 root logger 上，通过 `message_received` pyqtSignal 将日志安全传递到 UI 线程的 `log_view`。用于 Agent 对话、工具执行等常态日志。
2. **`_log_buffer` + QTimer 轮询**（同步期间）：同步期间 `QSignalLogHandler._sync_active=True`，跳过 RAG 日志避免与轮询并发操作 `log_view` 导致崩溃。RAG engine 通过 `log_callback` 参数直接把日志写入 `_log_buffer`（`threading.Lock` 保护），主线程的 `QTimer` 每 100ms 轮询消费 buffer 并 `appendPlainText`。

**为什么不用 Qt queued signal**：ONNX Runtime 在 `embed()` 期间持有 GIL 做 C++ 计算，Qt 的 queued signal 需要主线程事件循环处理，但 GIL 被占用时事件循环无法执行。QTimer 的 `timeout` 回调也是在主线程事件循环中执行的，但只要 `_embed_chunks` 的子批次 `sleep(0.01)` 短暂释放 GIL，QTimer 回调就能插入执行并消费 buffer。

**分工**：
- **日志区域**（`log_view`）：显示详细的全链路日志（扫描→对比→解析→清洗→切片→向量化→清理→保存）。
- **底部状态栏**（`status_label`）：只显示进度摘要（如"同步中 3/4 (75%) — 已写入 80 切片"），不显示完整日志行，避免重复。

## 4. 核心数据流

### 4.1 内核三态自动机主循环

```
用户输入
  │
  ▼
Agent.run(user_input)                     ← 门面
  │
  ├─ skills.record_request(text)          ──→ 可能触发 on_skill_suggested
  ├─ restore_checkpoint()                 ← 从磁盘恢复 Session 的工作记忆
  │
  └─ KernelLoop.run(user_input)           ← 内核接管
       │
       └─ while turns_used < max_turns:       ★ 本次 run() 独立计数
            │
            ├─ [THINK]
            │   anchor  = session.anchor_prompt(extra=pending)   ← 折叠历史 + key_info
            │   rec     = session.start_turn(anchor)
            │   messages = session.build_messages(system_prompt(), anchor)
            │       = [system] + <earlier_context>(L3 折叠区) + [最近 K 轮原文]
            │   resp = llm.chat_stream(messages, tools, temperature)
            │     ├─ "content"   → on_content + token 速度统计
            │     ├─ "reasoning" → on_reasoning
            │     └─ "done"      → tool_calls, usage
            │
            ├─ [THINK 分支]
            │   ├─ 空回复        → retry（≤3 次）后按 DONE 收尾
            │   ├─ 只吐代码块    → reask 一次；再犯则收尾（防死循环）
            │   ├─ 上下文超长    → non-fatal，转 CONSOLIDATE 兜底收缩
            │   ├─ 传输异常      → EXIT(ERROR)
            │   ├─ 无 tool_calls → finish_turn(L2 摘要) → EXIT(DONE)
            │   └─ 有 tool_calls → 进入 ACT
            │
            ├─ [ACT]
            │   maxlen = budget.remaining_for_tool(len(calls), max_tool_chars)
            │   for tc in tool_calls:
            │     ├─ parse_args       ← JSON 失败必须报回模型，不能当 {} 误诊
            │     ├─ should_confirm → callbacks.confirm（默认拒绝）
            │     ├─ on_tool_start / execute / on_tool_end
            │     └─ L0 捕获 → L1 裁剪(maxlen) → tool_results
            │   finish_turn(assistant_text, tool_calls, tool_results, L2 摘要)
            │   ├─ ask_user        → EXIT(INTERRUPT)
            │   ├─ 取消 / 致命错误 → EXIT(CANCELLED / ERROR)
            │   └─ 其余            → 进入 CONSOLIDATE
            │
            └─ [CONSOLIDATE]   ← 不调 LLM，只做信息减熵
                ├─ 预算告罄 或 每 consolidate_every 轮
                │     → session.force_fold(n)：旧轮 → 一行摘要
                ├─ 仍未落回预算 → Agent._shrink_session()（LLM 摘要兜底）
                └─ 回到 THINK

  EXIT → hooks.finished() → L4 蒸馏 / 事实抽取 / 技能建议（异步 daemon 线程）
```

**关键设计点**：
- **历史恒定 O(1)**：旧实现把整条 `_history` 每轮重发（O(轮次)），超阈值才被动摘要。内核只发「折叠区 + 最近 K 轮」，大小与轮次无关——这是 30k 硬上限得以成立的**结构性**原因，而不是靠事后压缩救火。
- **轮次上限是 per-run**：`_turns_used` 在每次 `run()` 开头归零。用会话累计值会导致累计 15 轮后 Agent 彻底不再调 LLM。
- **悬挂 `tool` 消息在结构上不可能**：L3 折叠与 `Session._windows()` 都以「整轮」为单位切片，不需要像旧实现那样在切分边界把 `assistant(tool_calls)` 拉回来。
- **预算超支转嫁**：`system` / `tools` 超支从 `raw` 里扣，30k 是真约束不是记账。
- **并行度感知的 L1**：`remaining_for_tool(n)` 让并发 4 个工具时每个自动只拿 1/4 额度，工具代码零感知。
- **上下文超长单独分类**：不等同于传输异常，否则兜底收缩永远走不到。
- **兜底收缩**：单个巨型输出（如整本 PDF）一次性击穿预算时才启用 LLM 摘要式收缩，摘要持久化到 `workspace/memory.md`。
- **Token 估算策略**：API 报告 `reasoning_tokens` 时信任 API；否则用 `estimate_tokens()` 估算。
- **失败恢复门**（§11.22.1）：ACT 态对工具失败记账（连续失败 / 失败签名 / 步骤内失败数），
  并把恢复指令注入下一轮锚点——步骤失败不会停车等用户打「继续」，而是依据失败信息
  自动换方案：原样重试被点名禁止、连续失败要求先诊断、未充分尝试就标 blocked 会被守卫
  拦回；模型想文字收尾时，失败感知的反思门以更高预算（4 次）+ 引用最近错误的方式要求继续。

### 4.2 RAG 摄取流水线

```
ingest(force, progress_callback)
  │
  ├─ Step 1: 扫描 kb 目录 (rglob) → all_files
  │
  ├─ Step 2: 加载 manifest，分片
  │   ├─ 未修改（mtime + size 一致）→ 跳过，progress 回调
  │   └─ 新增/修改 → files_to_process
  │
  ├─ Step 3: 启动 worker 池（默认 4 线程，文件数不足时按文件数缩减）
  │   每个 worker 处理一个 file shard:
  │     ├─ _extract_with_docling(filepath)  ← 优先 docling, 回退 per-format
  │     │     docling 输出 Markdown 时跳过 clean/normalize
  │     ├─ 若 markdown 缓存有效（mtime ≤ 源文件）→ 读缓存
  │     │   否则 clean_text + normalize_markdown → 写 .md 缓存
  │     ├─ chunk_documents → doc_chunks（hybrid → semantic → recursive）
  │     ├─ 背压: q.put(item, timeout=2.0)  ← 队列满时阻塞
  │     └─ finally: q.put(_SENTINEL)
  │
  ├─ Step 4: 主线程消费队列
  │   _chunk_iter() 生成器:
  │     while sentinels_seen < num_workers:  ← 等于实际启动的线程数
  │       item = q.get(timeout=2.0)
  │       if item is _SENTINEL: sentinels_seen++; continue
  │       更新 manifest[filepath] = signature + content_hash + chunk_count
  │       for c in doc_chunks: yield c
│   store.add_streaming(_chunk_iter(), batch_size=20, on_batch)
│     ├─ 第一批: 决定 create_table 还是 add
│     ├─ 按 source hash 删除旧记录 (upsert)
│     └─ 每 20 条 embed + add 一次（内部再拆分 5 条/子批，子批间 sleep 释放 GIL）
  │
  ├─ Step 5: _cleanup_deleted_files
  │   manifest 中存在但 all_files 不存在的 → store.delete_by_source + 移除 manifest 条目
  │
  └─ Step 6: _save_manifest (原子写)
```

**关键设计点**：
- **背压机制**：`queue.Queue(maxsize=parallel_workers * 2)`，worker 超前产出时阻塞，避免内存堆积。
- **取消传播**：`_cancelled` 在 worker put 循环、主线程 get 循环、extract 前等多处检查；`store.add_streaming` 失败时主动 `cancel()` 让 worker 停止产出。
- **Sentinel 丢失保护**：若所有 worker 已退出但 sentinels 未收齐，主线程退出避免死锁。
- **Markdown 缓存**：基于源文件 mtime 判断是否需要重新解析，避免重复 OCR/PDF 解析。
- **日志实时显示**：`ingest()` 接受 `log_callback` 参数，engine 内部 `_log()` 辅助函数同时写 `logger.info()` 和 `log_callback`。`log_callback` 把日志写入 `_log_buffer`（Lock 保护），主线程 QTimer 每 100ms 消费。每个关键节点（解析/清洗/切片前后、批次写入）后调用 `_flush_logs()`（`progress_callback(-1,...)`）触发额外的 UI 刷新机会。
- **资源释放时机**：`SyncKnowledgeWorker.run()` 在 `finally` 中 `engine.close()` 后才 `emit sync_finished`，避免主线程 `reload_rag()` 与 worker 侧资源释放竞态。

### 4.3 RAG 检索流程

```
Agent tool_call: rag_search(query, top_k=3)
  │
  ▼
RagSearchTool.run(query)
  │
  ▼
RAGEngine.search(query, top_k)
  │
  ▼
VectorStore.search_with_rerank(query, top_k=3, candidate_multiplier=4, min_similarity=0.7)
  │
  ├─ 向量检索: VectorStore.search(query, top_k=12)
  │   ├─ _ef.embed_query(query)  ← 加 "search_query: " 前缀
  │   ├─ _normalize(query_vec)
  │   └─ table.search(query_vec).limit(12).to_list()
  │       → 转换 _distance 为 similarity ∈ [0,1]
  │
  ├─ BM25 检索: VectorStore.search_fts(query, top_k=12)
  │   ├─ _tokenize_for_fts(query)  ← jieba 分词
  │   └─ table.search(tokenized, query_type="fts").limit(12).to_list()
  │       → BM25 分数 (_score)
  │
  ├─ 合并去重: 按 (source, chunk_index) 去重，向量候选优先
  │
  └─ VectorStore.rerank(query, candidates, top_k=3, min_similarity=0.7)
      ├─ FastEmbed reranker 可用: reranker.rerank(query, [c["text"]...])（返回分数，自适应 sigmoid 归一化到 [0,1]）
      │   └─ _filter_by_similarity: 过滤 rerank_score < 0.7
      ├─ 不可用: 回退到距离分数排序（不强制 0.7 过滤）
      └─ 按 score 排序取 ≤ top_k
```

**Token 控制**：默认 3 条结果，单次 ≤ 1500 tokens（32768 上下文中占比 < 5%）。

### 4.4 五级信息压缩流程

```
L0 原始捕获  工具返回瞬间       l0_capture() 硬上限 head+tail      单条 ≤ 20K 字符
L1 工具级裁剪 注入本轮前        l1_trim(maxlen=RAW余额÷并发数)     单条 ≤ 6K 字符
L2 回合摘要  每轮 finish_turn   l2_summary() <summary> ≤30 字      每轮 ≤ 30 字
L3 会话折叠  预算告罄/每 N 轮   l3_fold() 旧轮 → 一行             折叠区 ≤ 40 行
L4 记忆蒸馏  任务完成/检查点    蒸馏 facts/lessons/skill           → 图谱 / SKILL.md
```

#### L3 折叠的触发与执行

```
Session._windows()
  ├─ cur       = turns[-1]        （当前进行中的轮）
  ├─ completed = turns[:-1]
  ├─ keep      = min(raw_turns, len(completed))
  ├─ while render(completed[-keep:] + [cur]) > quota.raw:  keep -= 1
  ├─ raw       = completed[-keep:] + [cur]     ← 原文区
  └─ old       = completed[:-keep]             ← 折叠区（→ 一行摘要）

CONSOLIDATE 态:
  ├─ 每 consolidate_every 轮  → force_fold(consolidate_every)
  └─ 预算告罄                 → 先 force_fold，仍不够则 _shrink_session()
```

折叠以「整轮」为单位 —— 因此 `assistant(tool_calls)` 与其全部 `tool` 结果要么一起保留、要么一起折叠，**不会出现悬挂 `tool` 消息**。旧实现在消息粒度上切分，必须靠事后「把前置 assistant 拉回保留段」来补救。

#### L4 蒸馏的落地路径

```
start_long_term_update（模型主动）
  └─ 置位 kernel.distill_requested
      └─ hooks.finished() → 蒸馏线程（daemon，非阻塞锁去重）
           ├─ 独立抽取 LLMClient（httpx 非线程安全）
           ├─ 蒸馏出 facts / lessons / skill
           ├─ facts    → 工作记忆 checkpoint（每轮回注）
           ├─ lessons  → 知识图谱（长期经验）
           └─ skill    → workspace/skills/<name>/SKILL.md（可复用能力）
```

**能力进化闭环**：

```
任务成功 ─┬─ start_long_term_update → 蒸馏 → memory_graph  （经验）
          ├─ skill_save             → 固化 → skills/**/SKILL.md（能力）
          └─ rag_ingest             → 灌入 → 本地知识库      （素材）
下次同类任务 → skill_semantic_search 命中 → skill_load → 直接复用
```

#### 兜底收缩（`Agent._shrink_session`）

五级压缩的前提是「信息可以分块到达」。单个巨型工具输出（整本 PDF、全表 dump）会一次性击穿预算，此时才启用旧的 LLM 摘要式收缩：

```
触发: L3 折叠用尽（fold-exhausted）仍未落回预算
  ├─ 若 turns ≤ 1：跳过（不能把唯一上下文也摘要掉）
  ├─ transcript = session.all_digest_lines()[-25:]
  ├─ LLM 摘要（temperature=0.2，persona=摘要器）
  ├─ 摘要 + 触发原因 → workspace/memory.md（原子写，带时间戳）
  ├─ 摘要行并入 session.extra_digest，被摘要的轮从 turns 移除
  └─ callbacks.on_context_shrunk(summary, reason)
```


### 4.5 工具分发流程

```
LLM done event → tool_calls = [{id, function: {name, arguments}}]

for tc in tool_calls:
  ├─ args = parse_args(raw_args)  ← JSON 解析
  │   失败: on_tool_start(name, {_raw_arguments}) + on_tool_end(name, ToolResult(False, error))
  │
  ├─ tool = registry.get(name)
  │   不存在: on_tool_start + registry.execute (返回 unknown tool 错误) + on_tool_end
  │
  ├─ needs_confirm = tool.should_confirm(args)
  │   True 且用户拒绝: on_tool_end(name, ToolResult(False, "User denied"))
  │   (不调 on_tool_start — "never started" 语义)
  │
  └─ on_tool_start(name, args)
     result = tool.run(**args)
     on_tool_end(name, result)
     history.append({role: tool, tool_call_id: tc.id, name, content: result.to_message()})
```

### 5.3 阻塞对话协议（confirm / ask_user）

```
Worker 线程                         UI 主线程
─────────                           ─────────
callbacks.confirm(msg)
  ├─ _confirm_event.clear()
  ├─ bridge.confirm_request.emit(msg)  ──→  _on_confirm_request(msg)
  └─ _confirm_event.wait(timeout=600)      ├─ QMessageBox.question(...)
                                            │  (UI 阻塞等用户点击)
                                            └─ set_confirm_result(reply == Yes)
                                                  ├─ _confirm_result = val
                                                  └─ _confirm_event.set()
  ← 被 set 唤醒
  return _confirm_result
```

- 超时 600s，避免 worker 永久卡死。
- `cancel()` 同时 set 两个 Event，让阻塞中的 `confirm`/`ask_user` 立即返回。
- **默认拒绝**：`_confirm_result` 初值为 `False`、`_ask_result` 初值为 `None`，且 `Event.wait()` 的返回值被检查——超时或事件丢失时返回「拒绝 / 无回答」，而不是沿用上一次的结果。`shell_run` / `code_run` 等高风险操作绝不能因为对话框没回话而被默认放行。
- `BridgeCallbacks.reset()` 在每轮 `_on_send` 前复位 `_cancelled` / 结果 / Event，避免「终止对话」后残留状态污染下一轮。

### 5.4 信号命名陷阱

**所有** `QThread` 子类的自定义完成信号都不能命名为 `finished` —— 会遮盖 QThread 内置的 `finished` 信号，导致 `deleteLater` 在 `run()` **内部**触发（在线程仍在运行时销毁它），而真正的 `finished`（run 返回后）反倒没有监听者。

- `SyncKnowledgeWorker`：`sync_finished` / `sync_failed` / `sync_progress`（正确）。
- `InstallDepsWorker`：原为 `finished = pyqtSignal(object)`（**错误**），已改为 `deps_finished`；`deleteLater` 改挂到内置 `finished`。
- 另外，`MainWindow._is_worker_running()` 包装 `isRunning()` 并吞掉 `RuntimeError`——`deleteLater` 执行后 QThread 的 C++ 对象已被销毁，直接调 `isRunning()` 会抛「wrapped C/C++ object has been deleted」。

### 5.5 技能建议的延迟显示

`on_skill_suggested` 在 agent run 期间到达，但**不在 streaming 过程中弹模态对话框**（会阻塞 UI 事件循环，导致 content/reasoning chunk 无法渲染）。技能建议被缓存到 `_pending_skill`，在 `_on_finished` 之后（worker 线程已 join）才显示对话框。

### 6.1 资源生命周期

### 6.2 显式释放的必要性

Python GC 无法及时回收以下 C++ 资源：
- **ONNX Runtime InferenceSession**（~137MB embedding int8 + ~570MB reranker int8）：引用计数 + 循环 GC 才会触发析构，期间内存不释放。Embedding 模型通过 `get_or_create_embedding_function()` 进程级单例共享（RAG + 知识图谱共用），避免加载两份；共享时不 `session.release()`，仅 `VectorStore.close()` 时解除引用。
- **LongTermMemory 单例**：缓存在 `ToolRegistry._long_memory_instance` 上，`shutdown()` 时 `lm.close()` 释放 LanceDB 连接；不调用则会随 `_rebuild_agent()` 泄漏。
- **LanceDB 连接**：持有文件句柄和 mmap。
- **MCP 子进程**：不 stop 会变成僵尸进程。

因此 `VectorStore.close()` 显式：
1. 调用 `InferenceSession.release()` 立即回收 C++ 堆。
2. `model.cpu()` 把 PyTorch tensor 移出 GPU。
3. 置 None 让 Python 引用消失。

### 6.3 `_rebuild_agent` 的清理顺序

应用配置时重建 agent：
1. `old_agent.tools.shutdown()` — 停 MCP 子进程、关 RAGEngine。
2. `old_llm.close()` — 关 httpx 连接。
3. 创建新 `LLMClient` + `Agent`。

**运行期间禁止重建**：`_on_apply_config` 检查 `_busy`，若 agent 正在运行则弹窗拒绝（否则会销毁正在使用的 tools/httpx）。

### 6.4 窗口关闭清理（`closeEvent`）

对每个 QThread worker：
1. `disconnect()` — 断开所有信号，让 emit 变 no-op。
2. 协作式 `cancel()`（若支持）。
3. `wait(timeout)` — 等 run 返回。
4. 仍存活则 `terminate()`（最后手段，不安全）。

之后：
- `agent.tools.shutdown()` — MCP 子进程 + RAGEngine。
- `agent.close()` — 释放事实抽取专用的独立 `LLMClient`（独立 httpx 连接池）。`_rebuild_agent()` 会做这一步，但**直接关闭窗口不走那条路径**，原先会泄漏该连接池。
- `llm.close()` — httpx 连接。

### 6.4.1 子进程与进程组

`shell_run` 和 MCP 都通过 `start_new_session=True` 让子进程自成进程组：

- **`shell_run`**：`shell=True` 会 spawn `sh -c …`，再 fork 出真实命令。只杀顶层 PID 会留下孙进程（后台服务、`pip`、`sleep`）成为孤儿。超时后用 `os.killpg(os.getpgid(pid), SIGTERM)`，3s 宽限后 `SIGKILL`，并关闭管道。
- **MCP**：`npx` 之类包装进程会再拉起真正的 server；`stop()` 同样用 `killpg` 回收整棵树。清理条件以 `_process` 为准（**不是** `_running`）——读线程的 `finally` 会在 server 自行退出时把 `_running` 置 False，若 `stop()` 据此提前 return，就没人 `wait()` 回收僵尸进程。

### 6.4.2 `_JsonStore` 的 atexit 泄漏

`atexit` 内部持有回调的强引用。旧实现在每个 `_JsonStore.__init__` 里 `atexit.register(...)` 且从不 `unregister`，于是每创建一个 store（LongTermMemory 重建、切换 workspace…）就永久新增一条回调及其闭包，进程生命周期内单调增长。

改为：模块级只注册**一个**全局回调 `_flush_all_stores`，遍历一个 `weakref.WeakSet` 中仍存活的 store。store 被 GC 后自动从 WeakSet 消失，回调数量恒为 1，且不会阻止 store 被回收。

`GraphMemoryStore` 同样使用防抖写（§6.4.3），其 `__init__` 也调 `_register_atexit_flush(self)` 挂到同一张表上——退出前必须落盘，否则防抖窗口内的改动静默丢失。


### 6.4.3 原子写与防抖写（`atomic_io.py`）

固定 ``path + ".tmp"`` 的写法在多 writer 场景下会互相 truncate 同一个临时文件，落盘半截或混合内容；写失败还会把 `.tmp` 残留下来被后续读取当成数据。`file_ops._atomic_write` 早已用 `mkstemp` 修过同类问题，但 `memory.py` / `graph_memory.py` / `skill_index.py` / `agent._append_summary_to_memory` / `engine._save_manifest` 五处没跟上。

新增 `src/agent/atomic_io.py` 收敛为两个入口：

- `atomic_write_text(path, content)` — `mkstemp` 唯一临时名 + 权限继承（目标已存在则沿用其权限，否则 `0o666 & ~umask`；mkstemp 默认 0600，直接 replace 会让文件突然变成「仅属主可读」）+ `fsync` + `os.replace` + `finally` 清理。
- `atomic_write_json(path, payload)` — 上述的 JSON 变体。
- `backup_corrupt(path)` — `_load` 解析失败时把坏文件改名为 `.corrupt-<时间戳>` 再空初始化。旧行为是记一条 warning 后按空数据继续，下一次 `_save()` 就把坏文件覆盖掉——用户数据（手工编辑写错、版本不兼容）静默丢失且无从排查。

**防抖写**（`_JsonStore` 与 `GraphMemoryStore._save`）：连续写入以 0.5s 最小间隔合并成一次落盘，避免 O(N²) I/O；`flush(force=True)` / `close()` / atexit 强制落盘。`reload()` 必须先把脏数据写回再读盘，否则「set 后 0.5s 内 reload」会把那次 set 静默丢弃。

### 6.5 RAG 资源竞态与解决

**问题**：`SyncKnowledgeWorker` 写完数据后，agent 的 `RAGEngine` 持有 stale 表句柄，看不到新数据。

**解决**：
- `SyncKnowledgeWorker.run()` 在 `finally` 中 `engine.close()` 释放 worker 侧资源后，才 `emit sync_finished`。
- UI 收到 `sync_finished` 后调用 `agent.tools.reload_rag()`，触发 `RAGEngine.reload()` 丢弃表句柄，下次操作重新打开。

### 6.6 日志控件并发崩溃与解决

**问题**：同步期间，`QSignalLogHandler` 的 queued signal 和 QTimer 轮询的 `appendPlainText` 同时操作 `log_view`，导致 PyQt6 内部断言失败调用 `abort()` 崩溃。

**解决**：
- `QSignalLogHandler._sync_active` 标志：同步开始时设为 `True`，`emit()` 中跳过 RAG 模块日志（`_RAG_LOG_PREFIXES` 匹配），避免与 QTimer 轮询竞争。
- 同步结束后恢复为 `False`，`QSignalLogHandler` 重新接管 RAG 日志。
- `_log_buffer` 用 `threading.Lock` 保护，确保多 worker 线程写入与主线程消费的原子性。

## 7. 错误处理

### 7.1 错误传播路径

```
工具层错误
  ├─ Tool.run() 抛异常 → ToolRegistry.execute 捕获 → ToolResult(False, error)
  └─ ToolResult 通过 on_tool_end 回调 → UI 显示，并写入 history 作为 tool message

Agent 层错误
  ├─ LLM stream 异常:
  │   ├─ context_length_exceeded → 被动收缩重试（最多 3 次）
  │   └─ 其他 → on_error + on_finished, 退出 run()
  ├─ parse_args 失败 → 报错给模型（写入 history），继续下一轮
  └─ 达到 max_iterations → on_finished, 返回当前 final_content

UI 层错误
  ├─ _rebuild_agent 失败 → on_error 弹窗
  ├─ sync 失败 → sync_failed 信号 → QMessageBox.critical
  └─ worker 异常 → bridge.error 信号 → _on_error 显示

RAG 层错误
  ├─ 单文件 extract 失败 → 记录到 stats["errors"], 跳过该文件
  ├─ 单文件 clean/chunk 失败 → 记录 + 跳过
  ├─ VectorStore add 批次失败 → 记录, 单批失败不中断（连续 ≥3 批才中断）
  └─ manifest 更新失败 → 警告日志, 不影响已写入的向量

MCP 层错误
  ├─ 命令不存在 → MCPError, ToolRegistry 跳过该 server
  ├─ 请求超时 → MCPError
  ├─ 子进程崩溃 → reader 线程退出, pending 请求回填错误响应
  └─ JSON 解析失败 → 警告日志, 跳过该行
```

### 7.2 防御性设计

- **JSON 持久化**：所有 `_JsonStore` 加载时 `try/except (OSError, json.JSONDecodeError)`，损坏文件回退到 `{}`。
- **类型防御**：`LongTermMemory` / `GraphMemoryStore` / `SkillManager` 加载后 `isinstance` 检查，None/损坏数据重置为空结构。
- **config 迁移**：`_migrate()` 把过期的 embedding 模型名（含非量化→量化升级）/ 过小的 `max_tokens` 自动升级到当前默认。
- **记忆迁移**：`LongTermMemory.__init__` 首次加载时自动将旧扁平事实列表迁移到知识图谱。
- **事实抽取容错**：`extract_facts_via_llm` 容忍 markdown 围栏、JSON 解析失败、LLM 异常，任何错误返回空图谱。
- **Embedding 单例共享**：`get_or_create_embedding_function()` 进程级单例，`_EF_SINGLETONS_LOCK` 保护并发初始化。`VectorStore.close()` 检查 `is_shared`，共享时不 `session.release()`（避免破坏其他调用方）。
- **LongTermMemory 单例**：`_get_long_memory(registry, config)` 缓存在 `ToolRegistry` 上，避免每次 tool 调用创建新实例泄漏 ONNX 模型。`shutdown()` 释放后置 None。
- **空操作回退**：`on_context_shrunk` 等回调用 `try/except` 包裹，避免 UI 异常影响 agent 循环。
- **悬挂消息修复**：`_trim_history` 和 `_shrink_context` 都确保 history 不以 `tool` 消息开头。

| fastembed 模型名 | HuggingFace 仓库 | 缓存目录（`~/.cache/fastembed/` 下） |
|---|---|---|
| `nomic-ai/nomic-embed-text-v1.5-Q` | `nomic-ai/nomic-embed-text-v1.5` | `models--nomic-ai--nomic-embed-text-v1.5` |
| `BAAI/bge-reranker-v2-m3-int8` | `onnx-community/bge-reranker-v2-m3-ONNX` | `models--onnx-community--bge-reranker-v2-m3-ONNX` |

因此手工下载必须落到 `~/.cache/fastembed`（下到默认的 `~/.cache/huggingface` fastembed 看不到），且 `deps._is_*_cached()` 按仓库名 + 文件清单 + blob 完整性探测——`lazy_load=True` 只跳过 ONNX Session 创建，部分 fastembed 版本的下载逻辑在基类 `__init__`，用它探测会让「依赖检查」这一步就触发 137MB / ~570MB 下载。

**reranker 归一化**：`rerank()` 在首次打分时探测一次输出范围并**按模型固定**决定是否做 sigmoid（不再按「本批候选」自适应），保证 `min_similarity=0.7` 这个绝对阈值在不同查询间语义一致；sigmoid 用数值稳定写法，避免大负数 `exp` 溢出被外层 except 吞掉后静默回退。

## 11. 缺陷修复记录（本轮全量复查）

按影响面排序。每条均附根因与修复方式，便于回归定位。

### 11.1 致命：首次知识库同步永久卡死（死锁）

**现象**：全新安装、第一次点「同步知识」时，同步永远停在「同步中」，日志不再刷新。

**根因**：`VectorStore.upsert_document()` 先 `with self._documents_lock:`，再调用 `_ensure_documents_table()`；后者在 `_documents_table is None`（documents 表还没建）时再次 `with self._documents_lock:` —— 普通 `Lock` 不可重入，**自锁死**。ingest worker 卡在 `upsert_document`，主线程卡在 `q.get()`，双方无限等待。
之所以不是每次都触发：`_ensure_initialized()` 会顺手打开已存在的 documents 表，只有"表还不存在"这一条路径会死。

**修复**：`_documents_lock` 改为 `RLock`；并把建表逻辑拆成 `_ensure_documents_table_locked()`（假定已持锁），`upsert_document` / `delete_document` 在锁内直接调用它，不再嵌套 acquire。

### 11.2 `InstallDepsWorker.finished` 遮盖 `QThread.finished`

自定义 `finished = pyqtSignal(object)` 遮盖了内置信号，导致 `deleteLater` 在 `run()` 内部（还在运行时）被触发销毁线程；且 `_deps_worker.isRunning()` 可能抛 RuntimeError。已改名为 `deps_finished`，`deleteLater` 改挂内置 `finished`。

### 11.3 确认弹窗超时即默认放行

`Event.wait()` 返回值被丢弃，`_confirm_result` 初值为 `True`。对话框因任何原因没有回话时，`shell_run` / `code_run` 会被自动放行。改为初值 `False` + 检查 `wait()` 返回值；`ask_user` 同理返回 `None`，并新增 `reset()` 防止跨轮残留。

### 11.4 `skill_load` 任意文件读取（路径穿越）

`entry` 来自模型且未校验：`os.path.join(abs_dir, entry)` 在 `entry` 为绝对路径时直接丢弃 `abs_dir`，`../../` 又能逃出技能目录 —— 合起来等于允许读取磁盘任意文件。修复：入口名显式拒绝绝对路径与含 `..` 的分段；解析后再用 `realpath` 前缀校验；拒绝时**直接报错**，不允许回退到别的文件把非法请求伪装成成功。
同时修复了老技能（`skill.json` 声明 `entry: prompt.md`）用默认 `SKILL.md` 永远读不到内容的问题。

### 11.5 语义切片无视注入的 embedding function

`chunk_documents()` 从不把 `embedding_function` 往下传，`semantic_chunker._shared_embedding_function()` 因此总是去加载共享的本地 ONNX 模型：注入了自定义 EF（测试 `fake_ef`、未来的远端 embedding）也无效，离线环境还会卡在模型下载上。修复：`chunk_documents` → `_chunk_with_hybrid_fallback` → `hybrid_chunk_text` / `semantic_chunk_text` 全链路透传；`RAGEngine` 传入 `self._custom_ef`。
另外 `_shared_ef_resolved` 原在加载**前**置位，首次失败会被永久缓存，之后即使网络恢复也不再重试；改为只在成功时置位，并加锁避免并发重复加载。

### 11.6 切片文本包含原文中不存在的内容

两处拼接凭空造字符，导致 chunk 文本不是原文的连续子串（模型会看到源文件里没有的内容）：

- `semantic_chunker._tail_by_tokens()`：用 `re.split` 拆句后 `"".join` 拼回，分隔符里的 `\s*` / `\n` 被丢弃。改为在原文中定位句末边界后**直接切片**。
- `_merge_to_target_size()` / `_apply_overlap()`：硬编码 `"\n\n"` 作为连接符。改为 `_gap_between(source, left, right)` 取出源码里两片段之间**真实的间隔**。

### 11.7 docling 转换器：锁创建竞态 + `convert()` 完全无锁

`_converter_lock` 惰性创建（`if _converter_lock is None: ...`）是典型的 check-then-act 竞态，两个线程会各建一把锁、各建一个 `DocumentConverter`（数百 MB ×2）；而真正重入的 `converter.convert()` 却**完全没有加锁**，4 个 worker 并发调用未声明线程安全的转换器。修复：锁在模块导入时创建；`convert()` 用同一把锁串行化；新增 `release_converter()` 并在 `RAGEngine.close()` 调用（docling 模型不再常驻）。

### 11.8 `shell_run` 超时留下孤儿进程 + 输出无上限

`subprocess.run(capture_output=True)` 只 SIGKILL 顶层 `sh`，孙进程存活并继续持有管道；`capture_output` 全量读入内存，一条 `cat 大日志` 就能打满内存。改为 `Popen(start_new_session=True)` + 线程流式读取 + 进程组 SIGTERM/SIGKILL + 输出上限 200KB（超过则截断并标注）。

### 11.9 MCP `stop()` 留下僵尸进程

`stop()` 以 `not self._running` 为提前返回条件，而读线程在服务自行退出时会把 `_running` 置 False —— 这条路径跳过了 `terminate()`/`wait()`，子进程永远无人回收；若服务仍存活（仅 stdout 关闭）则成孤儿。修复：以 `_process` 为清理条件，`_running` 只作循环标志；加 `start_new_session=True` 并用 `killpg` 回收整棵树；关闭 stdin/stdout/stderr 三条管道（原先每次 rebuild 泄漏 fd）。
另外 `_read_loop` 对**迟到响应**（对应 `_call()` 已超时）无条件写入 `_results`，这些条目无人 pop，会永久驻留；改为丢弃。

### 11.10 配置：损坏即无法启动 / 静默篡改用户设置 / 非原子写

- `load()` 直接 `json.load`，写崩的 config.json 会让程序起不来 → 捕获异常后备份为 `.corrupt` 并用默认配置启动；同时对数值字段做类型强制（手工编辑常写成 `"32768"`）。
- `_migrate()` 把任何 `< 8192` 的 `max_tokens` 改成 32768，用户为本地 4K 模型显式设置的 4096/2048 每次启动都被改回 → 只在值等于旧默认 4096 时才迁移。
- `save()` 直接 `open(path,"w")`，写一半崩溃会留下截断的 JSON → 改为临时文件 + `fsync` + `os.replace` 原子替换。

### 11.11 技能索引：目录不存在时每次查询都写盘 + mtime 失效 + 锁外遍历

- `scan()` 在目录不存在分支只 `_save()` 不更新 `_last_scan`，导致 `_should_scan()` 恒为真：每次 `search()` 都 `makedirs` + 重写 `_index.json`。
- `_dir_mtime()` 只 stat 子目录，改写 `skill.json`/`prompt.md` 不改变目录 mtime，索引最迟 300s 才更新 → 现在同时 stat 目录本身与各 `skill.json`。
- `search()` 在 `scan()` 后不加锁遍历 `self._index` → 改为锁内取快照。
- `_load()` 的 `except` 未覆盖 `TypeError/AttributeError`（索引文件根不是 dict 时）→ 补全异常类型并校验结构。

### 11.12 `skill_retriever`：先删表后探测 → embedding 失败即丢索引

`build()` 先 `drop_table` 再探测 embedding 维度，一旦模型未下载/网络故障，已有可用索引已经被删掉。改为**先探测维度，成功后再删表重建**。
另外 `sync()` 用 `to_arrow().to_pylist()` 把含两条 768 维向量的整表读成 Python 对象（数千技能 ≈ 百万级 float），改为 `select(["dir","fingerprint"])` 只取需要的两列；`dir` 拼进 SQL 字面量前做 `''` 转义（目录名含单引号会让过滤表达式语法错误）；`close()` 真正调用 `db.close()`；扫描器 `_dir_mtime()` 只 stat 目录与 `SKILL.md`（原来 stat 每个文件，且每次查询走两遍全树）；BM25-only 候选的相似度查询只算一次 query 向量后复用。

### 11.13 `skills.py`：损坏记录拖垮整轮 + 请求表无界增长

`Skill(**s)` 与 `s["name"]` 遇到非 dict / 缺字段记录会抛 `TypeError`/`KeyError`，连带 `match()` 与 `record_request()` 一起失败 → 读取时逐条校验并跳过坏记录。
`requests` 计数表只增不删，长期使用的 `skills.json` 无界膨胀 → 超过 500 条时淘汰最旧的一半。停用词集合提到模块级（原来每轮对话重建）。

### 11.14 其他

### 11.17 工具层遗留限制根治（第四轮）

上一轮（§11.16）标记为「已知限制」的两个问题，本轮一并解决：

**`execute()` 签名级参数预检**（`base.py`）

旧实现靠捕获 `run()` 抛出的 `TypeError` 判定「参数无效」——但 `TypeError` 同时也是工具内部 bug 的常见形态（`len(42)`、对 None 做运算等）。两者混在一起时，工具内部出错会被报成 "Invalid arguments"，模型据此反复重试同样的调用，永远意识不到是工具坏了。

修复：调用前先用 `inspect.signature(tool.run).bind(**args)` 做签名预检——
- 预检失败（缺参/多参/非 dict）→ `Invalid arguments for <name>`，模型可修正调用；
- 预检通过后 `run()` 再抛 `TypeError` → 明确报告 `<name> failed internally (not an argument problem)` 并 `logger.exception` 留痕。

**`code_run` 的 stdout 恢复权全部移交主线程**（`code_run.py`）

旧实现 worker 在自己的 `finally` 里恢复 `sys.stdout/sys.stderr`。正常路径下主线程 join 后也会恢复，两者冗余；但超时泄漏的线程会在**未来任意时刻**退出并触发它的 finally——把 stdout 恢复成「它启动时的值」。若此时恰好有下一次 `code_run` 在执行（已换上自己的 StringIO），那次执行的输出会被整个吞掉。

修复：worker 只负责切换（`os.chdir` + 替换 stdout/stderr），**不做任何恢复**；主线程在 join 后无条件统一恢复。这样泄漏线程退出时只往自己的 StringIO 写，不再触碰任何全局状态，与前一次超时泄漏并发的后续 `code_run` 是安全的。

两个行为均有回归测试覆盖（`test_execute_distinguishes_internal_typeerror`、`test_code_run_leaked_thread_does_not_hijack_stdout`）。

### 11.18 第五轮：pytest-qt 环境补齐 + `_JsonStore` reload 数据丢失

**环境**：PyPI 主站与清华镜像对本机不可达（403/超时），改用阿里云镜像装上 `pytest-qt`——`test_bridge.py` / `test_integration.py` / `test_ui_flow.py` 三个 UI 测试文件得以首次在本机完整执行。

**`_JsonStore.reload()` 丢弃防抖窗口内的未落盘写入**（`memory.py`，真实数据丢失）

`_JsonStore` 采用防抖写入：0.5s 内多次 `set()` 只在最后一次落盘（`set()` → `_dirty=True` + 间隔够长才 `_save()`）。而 `reload()` 直接 `_load()` 用磁盘内容**整体覆盖** `_data`——若 reload 距上一次 `set()` 不足 0.5s，那次 set 的内容**还没写到磁盘**，就被磁盘旧数据覆盖，静默丢失。

触发链路（用户可感知）：`main_window._show_pending_skill_dialog()` 在 `create_skill()` 保存技能后立刻调用 `skills.reload()` 防止重复建议——但本轮对话的 `record_request()` 写入若发生在 0.5s 内（快速响应/缓存命中时），`create_skill` 的写入仍在防抖窗口里，`reload()` 一执行，**用户刚固化的技能直接丢失**，且无任何报错。

修复：`reload()` 在 `_load()` 前先把脏数据强制写回（`if self._dirty: self._save()`）。语义上 reload 的前提是「我的内存状态已安全持久化，需要吸收外部修改」，旧实现违背了这一前提。

发现过程值得一提：该问题先以「测试顺序相关的偶发失败」暴露——`test_skill_suggestion_cached_during_run_shown_after_finish` 单独跑必过、与其它 UI 测试同跑必挂。通过给 `_JsonStore._save/_load/reload` 打桩对比两种场景的存储事件序列，确认隔离运行时防抖窗口恰好擦肩而过（时序侥幸），组合运行时窗口命中。**测试通过不等于没有 bug——这次是时序侥幸掩盖了数据丢失。**

回归测试：`test_json_store_reload_flushes_pending_writes`（内存与磁盘双重断言）。

| 位置 | 问题 | 后果 |
|---|---|---|
| `add_streaming` 单批提前 `return` | 跳过末尾的 FTS 重建 | 小知识库（<20 切片）同步后 BM25 查不到新数据，混合检索退化成纯向量，**无任何报错** |
| `delete_by_source` | 删向量后不置 `_fts_ready = False` | 已删除文档的 term 仍在倒排索引里，被关键词检索召回并交给 LLM |
| `reload()` | 只重置 `_table` | 同步后 `rag_outline` 读到旧 digest、BM25 看不到新切片 |

修复：提前出口同样重建索引；删除后失效标记；`reload()` 一并重置 documents 表/缓存/FTS 两个标志。

设计要点：这三条都不会抛异常、也不会让测试变红——**失效是静默的**。因此修复时统一在「数据变更」与「句柄刷新」两个语义点强制失效，而不是依赖调用方记得。

#### 11.19.2 documents 表存全文 Markdown（第三份冗余 + 无界内存）

`build_and_store_digest()` 把整篇 markdown 传给 `upsert_document`，而 `rag_outline` 只读 `digest`——**`markdown` 列零消费者**。语料因此在磁盘存 3 份（源文件、`rag/documents/*.md`、LanceDB 表），且 `_documents_cache` 全量载入后常驻进程（≈ 整个知识库字符量）。

修复：表内不再存全文，改存 `md_path`（指向已有缓存）；`_load_documents()` 按列读取并在写缓存前显式 `pop("markdown")` 兼容旧数据；`_ensure_documents_table_locked()` 建表时不再建该列。附带修复 M5（缓存读写未加锁导致「旧快照被写回」的竞态）——`_load_documents` 整体纳入 `_documents_lock`。

#### 11.19.3 UI 生命周期：`_fetch_worker` 从不置 None → 关闭窗口必崩

`FetchModelsWorker` 挂了 `deleteLater`，但 `_on_models_fetched` / `_on_fetch_failed` 都没清空 `self._fetch_worker`。此后 `closeEvent` 调 `isRunning()` 抛 `RuntimeError: wrapped C/C++ object has been deleted`；该异常从 `closeEvent`（虚函数重写）逃出，PyQt 5.5+ 默认 `qFatal()` → **进程 abort**。触发路径很普通：获取模型成功后关闭窗口。

修复：两个槽都清空引用；`closeEvent` 里 4 个 worker 与 `_on_stop_sync` 的两处判断**统一改用 `_is_worker_running()`**（该函数本就是为这个问题写的，之前有 6 处绕过它）。

#### 11.19.4 并发与阻塞

- **确认弹窗被抽取线程阻塞最长一个 LLM 请求**：`_get_extract_llm()` 无条件 `with self._fact_extract_lock`，而抽取线程在**整个 LLM 调用期间**持锁。修复：非阻塞 `acquire(blocking=False)`，取不到直接复用 `self.llm` 走本次调用——实现终于与「不延迟确认弹窗」的注释意图一致。
- **`_load_documents` 缓存读写无锁**：见 11.19.2。
- **`_get_skill_index` 完全无锁**：并发首次调用产生两个 `SkillIndex`（构造即全目录扫描 + 落盘）。修复：模块级锁 + 双重检查。
- **`GraphMemoryStore.close()` 只置 None 从不 close**：每次「应用配置」泄漏一个 LanceDB 连接。修复：显式 `close()` 并重置 `_vec_tried`（否则 close 后无法重新初始化）。

#### 11.19.5 功能正确性

- **`memory_search` 关键词兜底路径完全忽略 `top_k`**：未装 rag 可选依赖时（默认路径）一次宽泛查询会灌入全部 observation，与工具里其他地方的钳制自相矛盾。修复：`_keyword_search(query, top_k)` 生效。
- **技能分词 `\w+` 对中文失效**：`"提取pdf表格"` 成为单个 token，关键词 `pdf`/`提取` 永远不在集合里，中文技能检索恒为 0 分。修复：`_keywords_of()` 额外切出 CJK 整串 + 字符 bigram。
- **`usage` 字段为 `null` 时整轮崩溃**：`api_total = usage.get("total_tokens", 0)` 在网关返回 null 时得到 `None`，`None > 0` 抛 TypeError，且该段**不在 try 保护范围内** → 异常穿出 `run()`，回复丢失。修复：`usage.get(x) or 0` 归一（两处）。
- **工具层 RAG 引擎初始化在 try 之外**：知识库目录不可创建时，异常冒泡到 `ToolRegistry.__init__` → **文件/shell/web 等所有工具一起失效**。修复：整段包 try，失败仅跳过 RAG 工具。
- **`shell_run` 的 `timeout` 无钳制**（`code_run` 有）：传 99999 → 阻塞 27h 且无法被「终止对话」打断；传 0 → 立刻 kill。修复：钳制到 [1s, 600s]。
- **`web_scan` 流式失败 `except Exception: pass` 后静默重发**：真实超时会对同一 URL 再发一次完整请求（最坏 2×30s、重复流量），已读内容整段丢弃。修复：仅 `AttributeError`（替身无 `stream`）才回退，传输错误直接上抛。
- **`_reranker_state` 打分失败后停在 `"done"` 而模型为 None**：状态机失真。修复：同步置 `"failed"`。

#### 11.19.6 Prompt 效率与有效性

全仓 prompt 基线约 1,400–1,600 tok/轮。本轮改动：

**精简（约 −100 tok/轮）**：SYSTEM_PROMPT 删除模型已知的 function-calling 协议说明、`content`/`reasoning_content` 字段释义、以及可由前件推断的反例；摘要 prompt 合并重复条目；代码用途 prompt 压缩四重限定。

**补充两条高价值约束（+30 tok，收益远大于成本）**：
1. **语义检索 query 语言**：`memory_search`/`skill_semantic_search`/`rag_search` 必须用用户原始措辞，禁止翻译/音译成拼音。这条直接对应真实故障——模型曾把「回归神主旨」转成 `regui shi zhu zhi`，导致向量与 BM25 双通道同时落空、静默返回 0 条。此前只有 `rag_search` 的参数描述里有这条，其余两个检索工具完全没有。
2. **工具报错后的行为**：修正参数重试，连续两次同样失败即换方法或 `ask_user`，不要无限重试（仓库注释里记录了模型原样重试同一调用的失败模式）。

**修正不准确描述**：`skill_search` 返回值、确认范围（补上外部 MCP 工具）、`skill_semantic_search` 与 `skill_search` 扫描目录不同（`.agent/skills` vs `skills`，模型此前无从得知）、`webexec_js` 的不可达分支说明。

**注入上限（长会话下数量级收益）**：系统提示的动态注入段**不在上下文收缩范围内**（`_shrink_context` 只压 `_history`），因此必须各自设限：当天事实 ≤20 条 / 2000 字符 / 单条 120 字符，命中技能 prompt ≤1500 字符（并提示用 `skill_load` 读全文），持久化桶 ≤200 条；事实抽取 prompt 也加了 ≤5 实体 × 3 观察与语言约束。这是全仓最大的单项 token 节省点。

#### 11.19.7 上下文收缩阈值低估

`_estimate_history_tokens()` 只统计 system + history，而实际请求还带 `tools=self.tools.schemas()`——MCP 工具一多 schema 可达数千 token，完全不计入。加上 CJK 按 1.5 字符/token、代码按 4 字符/token 的低估，结果系统性偏小 → 主动收缩几乎不触发，保护只剩「API 报 context_length_exceeded 后被动收缩」（且上限 3 次）。

修复：把 tools schema 估算并入（按 history 长度缓存，避免每轮重复序列化）。

- 修复后 **361 个测试全部通过**（`tests/test_ui_flow.py`、`test_bridge.py`、`test_integration.py` 因本机缺少 `pytest-qt` 在 setup 阶段跳过，属环境预置问题，非代码回归）。
- `tests/test_documents_table.py`、`test_ensure_digests.py` 按新 schema（不再存 markdown）同步更新断言。

### 11.20 第七轮：内核重构（三态自动机 + 五级压缩）

参照 GenericAgent 内核（`agent_loop.py` / `agentmain.py` / `llmcore.py` / `ga.py`）对
`agent.py` 的单体 400 行循环做底层重构。设计文档见
[KERNEL_REFACTOR.md](KERNEL_REFACTOR.md)，模块职责见 §3.0。

**问题**：旧实现把整条 `_history` 每轮重发，prompt 大小是 **O(轮次)**；
唯一的保护是「估计值超过 `max_context_tokens × 90%` 时被动摘要」——
而该估计还漏算 tools schema、低估 CJK/代码密度，导致主动收缩几乎不触发。
上下文治理因此退化为「等 API 报 context_length_exceeded 再救火」。

**方案**：把控制流抽成内核，只保留三个状态；历史 / 能力 / 经验全部改为注入物。

| 关注点 | 归属 | 内核是否持有 |
|---|---|---|
| 历史 | `Session`（滚动折叠 L3 + 工作记忆 checkpoint） | ❌ 注入 |
| 能力 | `_ToolDispatcher` → `ToolRegistry`（`code_run` 为核心，`shell_run` 辅助） | ❌ 注入 |
| 经验 | `_AgentKernelHooks` → 知识图谱 / `skills/**/SKILL.md` / RAG | ❌ 注入 |
| 控制流 | `KernelLoop`（THINK / ACT / CONSOLIDATE） | ✅ 唯一职责 |

**工具补齐**（对齐 GenericAgent 的 9 个原子工具）：

- 新增 `update_working_checkpoint`（短期工作记忆，每轮自动回注）
- 新增 `start_long_term_update`（触发 L4 蒸馏）
- 新增 `skill_save`（能力进化写入端）
- 新增 `AliasTool`：`file_patch` ← `file_modify`、`web_execute_js` ← `webexec_js`
  （同一实现两个入口名，旧名不破坏既有模型行为）
- RAG / skill / memory / MCP 全部保留

**兼容性**：`Agent.run(user_input) -> str` 签名与返回不变，UI 零改动；
`AgentCallbacks` 全部保留；旧的上下文收缩保留为**兜底**路径。

**实测**：连续 10 轮读取 40K 字符文件的长任务，每轮 prompt 峰值均 ≤ 30 000 token
（`tests/test_kernel.py::test_prompt_stays_within_30k_over_long_run`）。

### 11.21 第八轮：内核实现复查（P0 三项 + 工具/RAG/UI 修复）

重构落地后对全部代码做了一轮实现级复查。前三项是内核自身缺陷，其中第一项是致命的。

#### 11.21.1 内核 P0

**`max_turns` 用会话累计轮次判定**（致命）

`KernelLoop.run()` 的循环条件写成 `while session.current_turn < self.max_turns`，
而 `current_turn` 是**会话累计**轮次。后果：用户累计对话 15 轮之后，
Agent **彻底不再调用 LLM**，每轮直接返回「已达最大轮次」——
渐进劣化、无异常、极难察觉。修复：引入 `_turns_used`，每次 `run()` 开头归零。

**reask 分支丢失最终答复轮**

模型「只吐代码块、不调工具」时会先 `_rollback_turn(rec)` 再 `finish_turn(rec, ...)`。
`rec` 已从 Session 摘掉，写的是一个游离对象 → 最终答复轮根本没进历史，
L4 蒸馏也永远拿不到结论。修复：不在回滚分支里 `finish_turn`；
同时加 `_reask_guard`，提示一次后仍犯则直接收尾（防死循环）。

**周期性 CONSOLIDATE 完全空操作**

`do_consolidate` 传的是 `force_fold(0)`，即「折叠 0 轮」——
turns 单调增长、`extra_digest` 永远为空，L3 只在预算告罄时才被动触发。
修复：传 `consolidate_every`。

**其余内核修复**：预算漏算 `tool_calls` 参数体（并发 8 个代码类工具会静默突破 30k）；
`system` / `tools` 超支不从 `raw` 扣除（30k 沦为记账）；
`estimate_tokens` 字符密度过乐观；上下文超长被归类为致命错误导致兜底收缩永远走不到；
蒸馏线程无并发上限且会退回共享 `httpx.Client`（正是独立抽取客户端存在的意义）。

#### 11.21.2 工具层

- **`skill_save` 保存的技能永远进不了向量索引**：调用 `scanner.scan(force=True)` 会
  刷新 `_last_scan` / `_last_mtime`，于是 `ensure_indexed()` 的 `_should_scan()` 恒为
  False —— 索引停在首建快照，`skill_semantic_search` 永远召不回刚保存的技能。
  修复：改用 `mark_stale()`。
- **`code_run` 超时线程污染真实 stdout**：注释声称「只往自己的 StringIO 写」是错的。
  `print()` 每次都动态查找 `sys.stdout`，主线程超时后已恢复成真实 stdout，
  泄漏线程因此直接往**真实** stdout 打印（既不受 `_BoundedIO` 截断，也不进工具结果）。
  修复：超时后 close 缓冲区，其下一次写入抛 `ValueError`，线程自行退出。
- `SkillVectorStore.sync()` / `graph_memory` 回填的「读判重 → 写」不在锁内 → 并发重复行；
  回填标志在成功**前**置位 → 失败永不重试。
- `shell_run`：SIGTERM 后若 shell 先退出就跳过 SIGKILL（忽略 SIGTERM 的孙进程变孤儿）；
  僵尸不回收；新增 `atexit` 退出期回收。
- `mcp_client` 超时只清理 `_results` 的一半 → 泄漏完整响应体。
- `skill_search` / `skill_index` 参数未归一化（`int("abc")` 抛裸异常）；文件读取无上限。

#### 11.21.3 RAG

- **删除的文件被「复活」**：`_cleanup_deleted_files` 只删向量和元数据，
  Markdown 缓存没删；紧接着的 Step 7（`ensure_digests_for_cached_documents`）发现
  「有缓存文件、无 digest 记录」，于是用旧缓存重新生成一条。
  表现：日志打了「🗑 已清理」，但 `rag_outline` 仍列出该文档，
  `rag/documents/` 下的 `.md` 永久堆积。修复：清理时一并删缓存，
  并新增 `get_document_by_md_path` / `delete_document_by_md_path` 按 `md_path` 精确匹配。
- **`content_hash` 只写不读**：签名只看 mtime + size。`cp -p`、解压保留 mtime、
  `git checkout` 都会让「内容换了、签名没变」的文件被**永久**漏同步。
  修复：判为「本要跳过」时再算一次源文件字节指纹。
- **缓存文件名还原失真**：文件名经清洗（空格/括号/中文标点被丢弃）后，
  `Chapter 1.pdf` 被认成 `Chapter1.pdf`，每轮同步都判定「缺记录」并写入一条重复行。
  修复：优先按入库时原样记录的 `md_path` 匹配，文件名猜测只作老数据兜底。
- `clear()` 不重置 `_fts_ready`（对比 `close()` 已做）→ 清空后 BM25 静默失效。
- `_closed` 永不复位：实例被 `close()` 后重新初始化，reranker 对它永久降级且无日志。
- `ingest()` 的 `_log()` 回调无保护：异常穿出会让 `finally` 里的 `_abort.set()` 不执行，
  4 个 worker 永久阻塞在 `q.put(timeout=2.0)`，连同各自切片内存一起泄漏。
- docling 初始化失败即**永久**禁用（`_converter_unavailable` 无复位路径）：
  进程早期跑过一次 ingest（未安装 → 禁用），依赖检查自动装好后仍全程回退。
  新增 `reset_unavailable()`，在依赖安装成功后调用。
- docx / xlsx / pptx 解析句柄不关闭：4 worker × 数千文件累积句柄
  （Windows 上还会锁住文件）。改为 `try/finally` 显式关闭。

#### 11.21.4 UI

- **`_on_fetch_models` 覆盖仍在运行的 QThread**（进程 abort）：
  `self._fetch_worker = FetchModelsWorker(...)` 是旧 QThread **唯一的 Python 强引用**，
  直接覆盖会让其引用计数归零 → sip 立刻析构仍在运行的 C++ QThread，Qt6 下是
  `qFatal` 级 abort（线程还阻塞在 30s 超时的 `list_models` 里）。
  触发路径很普通：点「获取模型」→ 发一条消息 → 该轮结束重新 enable 按钮 → 再点一次。
  修复：与 sync/deps 一致，加 `_is_worker_running()` 并发守卫。
- **`closeEvent` 先 `terminate()` 再 `tools.shutdown()`**（关窗口挂死）：
  `terminate()` 不释放任何 Python/Qt 锁，被杀线程可能正持有
  `ToolRegistry._retriever_lock` / `MCPClient._lock` / `RAGEngine._store_lock`，
  之后 `with self._lock:` 会永久阻塞。修复：`terminate()` 后标记
  `_worker_terminated`，跳过所有需要取锁的释放动作，交给进程退出时由 OS 回收。
- **「终止对话」无兜底**：`_busy` 只在 `_on_finished` 复位，遇到不检查取消标志的阻塞点
  （MCP `tools/call` 300s、长 shell 子进程）就永久禁用发送/清空/应用配置/同步。
  修复：加 30s 看门狗 `QTimer`，超时强制收尾并复位 UI；正常收尾时撤掉看门狗。
- `_rebuild_agent` 失败后留下半死 agent：旧的已被 `tools.shutdown()`
  （MCP 子进程已杀、RAG 引擎已关）、旧的 llm 也 `close()` 了，但引用还在，
  用户照常点「发送」会拿到一个 MCP 全挂、httpx 已关的 agent。修复：失败即清空引用。
- 流式输出每 chunk 两次全文档光标操作（100 tok/s 时每秒数百次重绘）。
  改为 40ms 合并刷新（~25fps）；工具行与收尾前强制 flush，保证顺序正确。
- 日志 handler 用模块级全局：多窗口时先关的窗口会误删后建窗口的 handler，
  且从不置空。改为优先用实例引用，关闭后置空全局。

#### 11.21.5 未改动的两处（需权衡决策）

1. **流式期间强制钉在底部**：`_scroll_to_bottom` 无条件 `sb.setValue(maximum)`，
   用户往上翻看历史会被硬拽回底部。`test_ui_flow` 的两个用例**明确断言**了这个行为
   （"even after the user scrolled up"），属于作者的有意设计。
   复查认为是体验问题，但改动等于推翻已测契约，本轮保留原行为。
2. **docling 转换被全局锁串行化**：4 个 worker 对 PDF 实际退化为单线程。
   这是用并行度换线程安全（`DocumentConverter` 未声明线程安全），
   改成分片并行需要重写 `docling_parser` 的锁粒度。

### 11.22 第九轮：失败自动恢复 + 全量复查（bug / 泄漏 / 性能 / 体验）

#### 11.22.1 失败自动恢复（内核）

需求：计划中某项任务失败时，agent 应**依据失败信息自动找方案解决并继续后续任务**，
而不是停下等用户输入「继续」。原行为根因：单次工具失败本不会停车（失败作为 tool
结果回喂），但模型想用文字收尾时反思门只提醒 2 次就放行，并在结尾附上
「可回复『继续』让我接着做」——停车点在反思门。

内核新增四层机制（`KernelLoop`，每次 `run()` 重置记账）：

1. **失败感知反思门**：`_failed_total > 0` 时提醒预算 2→4 次；提醒文案引用
   最近一次失败的 `(工具名, 错误摘要)`，明确「依据失败信息自动解决」三步法
   （读完整错误 → 换方法重试 → 多种方法都不可行才标 blocked），并禁止停下来
   问用户是否继续。
2. **原样重试检测**：失败调用签名（工具名 + 排序参数 JSON，保留最近 8 条）；
   命中 → 点名「禁止重复」，要求换参数/换工具/用 `code_run` 写诊断脚本。
3. **连续失败提示**：`_fail_streak ≥ 2`（任一批全成功即清零）→ 要求先诊断再换
   方案，同一思路只试一次。
4. **防过早 blocked 守卫**：`update_plan` 把步骤标 `blocked` 时，若步骤边界
   （上次 update_plan 之后）失败次数 <2 → 提醒恢复 `doing` 换方案再试；
   守卫本身有 2 次上限，模型坚持放弃时最终尊重。标记 `skipped`（有意不做）
   不触发，避免误伤「用户明确说跳过」的场景。

配套：系统提示 rule 8 重写（失败不是停下的理由；blocked 前至少 2 种不同方法）；
`update_plan` 工具描述与 `status` 参数说明同步强化。回归测试
`tests/test_failure_recovery.py`（11 例）。

#### 11.22.1.1 自动续跑与任务边界（后续实测反馈）

实际使用暴露两类「必须人工输入继续」的残留路径，补齐：

1. **自动续跑**（`Agent.run`，`_AUTO_CONTINUE_MAX=2`）：两类停车不再甩回用户——
   ① `MAX_TURNS` 截断（长任务跑满轮次上限）；② `DONE` 但计划仍有 open 步骤
   （反思门提醒额度用尽，模型反复给文字总结）。每段续跑是完整的内核 run
   （轮次预算/反思门/失败恢复/取消全部生效，`_finish_nudge` 随 run 重置）；
   期间用户点「终止」立即停；额度用尽才交回用户并注入如实说明。开关：
   `agent._auto_continue`。注意内核把 LLM 异常折叠为 `ERROR` 出口，续跑循环
   不会把传输故障当「未完成」反复重试。
2. **反思门出口补全**：提醒文案明确「若该步骤的工作**实际已完成**，用
   `update_plan(op=patch, status=done)` 收尾，不要为响应提醒重复已完成的工作」
   ——此前只说「继续执行下一步」，模型认为工作已做完时只能再给一遍总结，
   提醒耗尽后停车等「继续」，而计划面板永远显示有一个未完成项。
3. **任务边界 fork 提示**：新请求到来而旧计划仍有 open 步骤时，`agent.run`
   经 `working["__plan_boundary__"]`（anchor 一次性消费）注入 fork 提示：
   强制模型显式判断「新任务 → `create` 替换计划 / 继续旧任务 → 接着做」。
   此前旧计划被静默沿用，表现为「新任务的计划与输入无关」。
4. **patch 自纠**：`update_plan` 用错 step_id 时报错附当前计划渲染。

#### 11.22.2 并发 / 泄漏

- **MCP `stdin.write()` 持锁无超时**：server 停止读取 stdin 时，64KB 管道写满后
  阻塞写会无限期挂起 agent 线程，且因持有写锁所有后续 `_call` 全部排队等死。
  改为**专用写线程 + 有界队列**（容量 64、入队超时 10s）：调用方只做有界入队，
  单消费者线程天然防消息交错（旧写锁的存在理由），最坏情况抛 `MCPError`；
  写失败立刻唤醒全部等待中的 `_call`（否则 `tools/call` 要干等 300s）。
- **RAG ingest 互斥锁是实例级**：UI 的 `SyncKnowledgeWorker` 与 agent 的
  `rag_ingest` 各自持有不同的 `RAGEngine`，实例级锁对这两条真实并发路径完全
  无效（同时写同一张 LanceDB 表、同时 `_save_manifest` 后者覆盖）。
  改为模块级按 `rag_dir` 键控的跨实例锁。
- **`graph.clear()` 不清 `_pending_index`**：此前嵌入失败入队的条目对应的 JSON
  实体已删，clear 后任何一次 add/search 会把它们写回新表——用户删掉的事实被
  语义检索**复活**。`clear()` 一并清空（带 `_pending_lock`）；pending 队列同时
  加专用锁（并发 swap/extend 丢条目）与 500 条上限（嵌入持续失败时内存只增）。
- **`ToolRegistry.shutdown()` 裸清单例**：与 `_get_long_memory` /
  `get_skill_retriever` 的懒初始化竞态——shutdown 清空后紧跟一次新建，新实例
  不在任何缓存里永不被 close（每次「应用配置」泄漏 ~137MB ONNX + LanceDB）。
  单例清空持 `_singleton_lock`。
- **FastEmbed 懒加载无锁**：`_ensure_model` 的 check-then-act 之间有 GIL 释放点，
  ingest worker / 主线程 / 检索 / graph_memory / skill_retriever 首次并发会各加载
  一份 ~137MB ONNX。进程级加载锁 + 双重检查。
- **reranker 状态裸写**：后台 `_load` 线程与 `close()` 都不持 `_reranker_lock`
  读写 `_reranker/_reranker_state`，交错时已 close 的实例「复活」持有 ~500MB
  权重，且 state=done 后还会再起加载线程。全部写回/close 持锁并在锁内复查
  `_closed`。
- **FTS 建索引跨实例并发**：写入侧（同步 worker 的实例）与检索侧（agent 的实例）
  对同一张磁盘表并发 `create_index(replace=True)`。模块级建索引锁 + 「已存在」容错。
- **shell_run 取消后子进程跑满自身超时（最长 600s）**：`_run_capture` 改 0.2s
  粒度轮询取消标志，命中即杀进程组；`code_run` 同法（旧实现取消后线程占 CPU
  且 sys.stdout 持续被替换）。
- **skill embedding 失败回退 `None`**：`SkillVectorStore._get_ef` 会悄悄自建默认
  模型单例——正是注释要避免的第二个 ~137MB 副本。显式回退到默认模型单例。

#### 11.22.3 正确性

- **documents 表 `doc_id` 用 basename**：不同子目录的同名文件（`a/report.pdf` 与
  `b/report.pdf`）doc_id 相同 → upsert 互相覆盖、删除误删另一文件元数据。
  改用 `md_path`（每篇文档唯一）哈希；同名旧行按 `doc_name + md_path 不匹配`
  兼容清理。
- **事实抽取结果不校验内部结构**：LLM 把实体返成字符串 / observations 混入非
  str / relation 缺字段时，下游 `ent.get()/o.strip()` 抛 AttributeError 被 agent
  的 except 吞掉——**整轮实体/关系全部丢弃**。`extract_facts_via_llm` 逐条归一化：
  坏条目跳过、好条目保留。
- **`memory_graph` 的 clear/delete_entity 不弹确认**：模型一次误调用清空长期记忆。
  `should_confirm` 对破坏性 op 返回 True。
- **`update_plan` patch 语义**：无 step_id 时旧实现把 note 写到「状态已匹配」的
  步骤上再 break（`[done, pending]` + `patch(status=done)` 污染第一步、漏掉第二
  步）；只给 note 会改写所有步骤。改为先筛目标集合再统一写入；只给 note 必须
  带 step_id。patch 深拷贝后改（原地改活字典在校验失败时留下半改状态）；
  append 的 id 跳过已占用；create 仅在全 pending 时提升 doing。
- **WorkMemory LRU 淘汰不传 `force`**：0.5s 防抖窗口内的写入被静默丢弃（注释
  声称「先落盘再丢弃」实际做不到）。淘汰路径 `flush(force=True)`。
- **`checkpoint` 无 session 时静默成功**：模型以为已写入实际什么都没存。显式失败。
- **MOBI latin-1 回退被 `del data` 废掉**：utf-8 分支提前释放字节，回退触发
  NameError 被 except 吞掉——非 utf-8 MOBI 静默返回空。
- **`rag_ingest` force 字符串 `"false"` 为真值**：意外触发全量重建。严格布尔解析。
- **file_read 按字节数判截断**：多字节 UTF-8（300KB 中文 ≈ 10 万字符）被误判
  截断。按字符增量读取判定。
- **file_write 现场翻转进程 umask**（`os.umask(0)` 再恢复）：进程级全局操作且非
  线程安全。导入期缓存一次。
- **config**：字符串字段 `str()` 把列表/字典存成 `"['x']"` 垃圾值 → 仅接受 str，
  否则回退默认；`save()` 固定 tmp 名在并发保存时互踩 → mkstemp 唯一名。
- **shell_run 无条件对 pgid 发 SIGKILL**：组主退出后 pgid 被 OS 回收复用，可能
  **误杀无关进程组**。组主活着直接杀；已退出先信号 0 探测组是否仍存在。
- **MCP stop 后 reader 阻塞**：server 存活时故意跳过关管道（防 close 挂死），
  reader 线程阻塞在 readline——不可杀进程（D 状态）下无解，属已知取舍。
- **UI 强杀后流式状态残留**：`<summary>` 已开未闭时强杀，下一回合整条回复被
  吞进 stripper 缓冲区——用户看到空回复。回合开始（`_on_send`）统一复位流式
  状态与 stripper；强杀路径先 `_flush_stream(final=True)` 落盘缓冲。
- **UI 强杀丢弃运行中 QThread 引用**：`wait(1000)` 超时后 `self._worker = None`
  会让 sip 析构运行中的 QThread → qFatal abort（MCP `tools/call` 300s 阻塞可命中）。
  超时挂 `_orphan_workers` 孤儿列表保留引用，`closeEvent` 再统一 wait；
  `_on_finished` 的 `wait(2000)` 同法。
- **`_worker_terminated` 永不复位**：一次强杀后每次退出都跳过
  `tools.shutdown()`/`agent.close()`（泄漏 MCP 子进程与连接池）。重建成功后复位。

- **skill 目录 mtime 探测**：5 分钟扫描间隔内每次检索因 `_should_scan` 全树 walk

### 11.23 第十轮：code_run / shell_run 风险分级确认

**需求**：非破坏性、不影响重要系统文件与安全的 `code_run` / `shell_run`
操作不再每次弹人工确认，直接执行。

**根因**：两工具 `destructive=True`，`Tool.should_confirm` 默认策略「destructive
即确认」——而 `code_run` 是能力核心（几乎每轮调用），高频弹窗把工作流切成碎片，
还诱导用户无脑点「Yes」，确认机制名存实亡。

**实现**（新增 `tools/risk.py`，纯静态启发式，读参数文本不执行）：

- `is_risky_command(cmd, workspace)`：sudo/doas、系统-电源控制（shutdown/
  reboot/pmset/csrutil/launchctl/nvram）、进程杀伤（kill/killall/pkill）、
  磁盘操作（diskutil/mkfs/dd）、管道下载执行（`curl … | sh`）、
  `git push --force`、以及「破坏性动词（rm/mv/chmod/tee/defaults…）或向绝对
  路径重定向」+ 工作区之外路径 → 弹确认。
- `is_risky_code(code, workspace)`：sudo、管道下载执行、git push --force、
  破坏性调用（`os.remove/unlink/rmdir/chmod/chown`、`shutil.rmtree`、
  `subprocess`、`os.system` 等）+ 工作区之外路径字面量**同现** → 弹确认。
- `mentions_outside_path`：剥 URL（防 `http://x/y` 误报为 `//x/y` 绝对路径）、
  `~` 展开、`../` 逃逸按 workspace 解析（shell 子进程不受写护栏约束）、
  realpath 前缀比对；`/dev/null` 等惯用法白名单。
- 两个工具覆写 `should_confirm`；`config.always_confirm_code=True` 一键恢复
  旧的逐次确认；MCP 工具保持逐次确认不变；确认弹窗展示逻辑（用途说明）
  不变。工作区内写护栏、超时、取消机制均不受影响。

**设计取舍**：静态启发式宁可漏报不可误杀——漏掉的破坏有写护栏与超时兜底，
误报的确认会让用户养成无脑放行的习惯。回归测试 `tests/test_confirm_policy.py`
（52 例）。

## 附录 A：关键性能优化

1. **流式 token 速度估算**：增量计数 `live_est_tokens += _estimate_tokens(chunk)`，每 0.3s 发射一次；总开销 O(N) 而非 O(N²)（避免每 0.3s 全量 join + 扫描）。
2. **TTFB 排除**：速度计算用 `gen_elapsed = now - ttfb`（不含 prefill 延迟），准确反映生成速度。
3. **chunker 增量计数**：维护 `cur_cjk` / `cur_other` 运行计数，避免 O(N²) 重复扫描。
4. **RAG 流式 ingest**：worker 池并行 + 有界队列背压 + 批量 embed，内存占用 O(workers × 单文件 chunks) + O(batch_size)，不随知识库总规模线性增长。
5. **OCR 全局单例**：4 worker 共享同一 RapidOCR 实例（~500MB），通过信号量串行调用，避免 ~2GB 重复加载。
6. **LanceDB 表不缓存"不存在"**：`_ensure_table()` 每次重查 `table_names()`，因为 SyncKnowledgeWorker 可能已创建表；目录 listing 很便宜。
7. **`list_sources` 用 pyarrow compute**：在 Arrow 层去重，避免把全部行转 Python 对象。
8. **子批次嵌入释放 GIL**：`_embed_chunks` 将每批 20 个 chunk 拆分为 5 条/子批，子批次间 `sleep(0.01)` 释放 GIL，让主线程 QTimer 能插入执行消费日志缓冲区，避免 ONNX Runtime 长时间持 GIL 导致 UI 冻结。
9. **QTimer 日志轮询**：同步期间用 100ms 间隔的 QTimer 直接在主线程事件循环中轮询 `_log_buffer`，绕过 Qt queued signal 机制（后者在 GIL 被占用时无法及时处理）。
10. **图谱观察批量嵌入**：`_index_observations_batch()` 用 `embed_documents()` 单次 ONNX 前向处理整批观察（事实抽取一次对话通常产生多条观察），替代逐条 `embed_query()` 的 N 次调用。
11. **技能索引防抖**：`SkillIndex` 以目录 mtime + 300s 间隔双重条件触发重建，常态 `skill_search` 只读 `_index.json`（O(1) 加载），不重复扫描目录。
12. **docling 单例**：`DocumentConverter` 进程级单例 + 双重检查锁，多 worker 共享一份 docling 模型（torch 模型重，避免重复加载）。
13. **Hybrid 分片三级回退**：结构+语义 → 纯语义 → 递归，chonkie/embedding 缺失时自动降级，不阻塞入库；语义分块复用向量存储的 nomic-embed-text 单例，避免加载第二份 ~137MB ONNX 模型。
14. **动态并发**：`num_workers = min(parallel_workers, len(files))`，文件数少于默认并发时按文件数缩减；哨兵计数 `expected_sentinels = num_workers`（与实际启动线程数一致），避免文件数不足时消费者空等 15s 兜底超时。
15. **混合检索召回增强**：向量相似度 + BM25 关键词双通道并行检索，兼顾语义召回与精确关键词命中；BM25 用 jieba 预分词（Python 层）+ 原生 FTS `simple` tokenizer。
16. **jieba 分词器单例**：`_get_jieba()` 进程级缓存 + 双重检查锁，避免每个切片重复初始化 jieba 词典（首次加载 ~0.7s）。
17. **文档元数据缓存**：`VectorStore._documents_cache` 缓存 documents 表内容，`get_document_digest`/`list_documents` 避免每次全表 `to_pylist()`；写入时失效。documents 表**不再存全文 Markdown**（只存 digest + chapters + md_path），缓存按列读取并剔除 markdown 列——既省磁盘第三份冗余，也避免整库常驻内存。
18. **Reranker 加载状态机**：`_get_reranker` 用 `_reranker_state`（idle/loading/done/failed）去重并发加载，避免多调用方各自起加载线程（每线程 ~500MB PyTorch 权重泄漏）；超时后后台线程完成仍写入结果供后续复用。
19. **OCR 引擎释放**：`parsers.release_ocr_engine()` 在 `RAGEngine.close()` 时释放全局 RapidOCR 单例（~500MB），避免 GUI 应用同步含图片 PDF 后常驻内存；下次入库懒加载重建。
20. **独立事实抽取客户端**：`Agent._get_extract_llm()` 为事实抽取 daemon 线程惰性创建独立 `LLMClient`（独立 `httpx.Client` 连接池），避免与对话线程并发争用同一个非线程安全的 `httpx.Client`；`Agent.close()` 释放该独立客户端，防止「应用配置」重建时泄漏连接池。
21. **`_estimate_tokens` 用 `str.translate`**：CJK 字符数通过预编译的删除表在 C 层统计，替换原先的 Python 逐字符循环（该函数在 token 速度估算、上下文收缩阈值判断等热路径上高频调用）。
22. **`estimate_tokens` 用 `finditer` 计数**：原来 `re.findall` 会把全部匹配物化成列表（整篇中文文档 = 数万个临时单字符串对象）；改为预编译 `_CJK_RE` + `sum(1 for _ in finditer(...))`，零中间列表。
23. **切片去重只存哈希**：`_split_by_tokens` 的 `seen` 集合原来存每个 chunk 全文（切片本身已是文档副本，等于峰值内存翻倍）；改为存 `hash(chunk)`。
24. **段落分组增量计数**：`hybrid_chunker._split_by_paragraph` 原来每追加一段就重新估算整个 `current`（O(n²)）；改为维护 `current_tokens` 运行计数。
25. **技能扫描只 stat 目录与 `SKILL.md`**：`SkillScanner._dir_mtime()` 原来 stat 每个文件，且 `_should_scan()` 与 `scan()` 各调一次 —— 单次检索两遍完整 `os.walk`。
26. **技能索引按 workspace 缓存**：`SkillIndex` / `SkillRetriever` 按目录路径缓存，避免切换 workspace 后重建，也避免错误复用。
27. **BM25-only 候选复用查询向量**：`SkillRetriever` 只为「仅 BM25 命中」的候选算一次 query 向量并复用，替代每个候选各跑一次 `embed_query`。
28. **`skill_retriever.sync()` 只取两列**：`to_arrow().select(["dir","fingerprint"])`，不再把两条 768 维向量列转成 Python float 列表。
29. **`list_sources` / `list_documents` 走缓存与列裁剪**：避免把 documents 表反复全量 `to_pylist()`。
30. **日志/对话控件限流**：`think_view` 10000 段、`log_view` 5000 段、`chat_view` 5000 段（`setMaximumBlockCount`），长会话不再无限增长。
31. **写入侧 source→hash 缓存**：`_embed_chunks` 内按批次缓存 `_hash_source`（同批 chunk 通常同源），避免每 chunk 重算 md5。
32. **tools schema token 估算缓存**：`_tool_schema_tokens()` 按 history 长度缓存，避免每轮为上下文收缩阈值重复序列化全部工具 schema。
33. **当天事实与技能注入限流**：系统提示的动态注入段不在上下文收缩范围内，故设条数/字符上限，长会话下避免提示单调膨胀（详见 11.19.6）。
34. **历史恒定 O(1)（内核）**：每轮只发「L3 折叠区 + 最近 K 轮原文」，prompt 大小与会话轮次无关。旧实现把整条 `_history` 每轮重发（O(轮次)），长会话下 I/O 与 prefill 成本线性增长——这是本轮最大的单项性能收益。
35. **预算超支转嫁**：`system` / `tools` 超支从 `raw` 扣除，避免各区各自记账导致总数失控。
36. **并行度感知的 L1 裁剪**：`remaining_for_tool(n)` 按「RAW 余额 ÷ 并发数」分配，并发 4 个工具时每个自动只拿 1/4，无需工具侧改动，也不会因单条巨型输出挤掉其余结果。
37. **L2 物理快照**：每轮结束即生成 ≤30 字摘要并冻结，之后即使原文被折叠也不会重新计算——折叠是 O(已折叠行数) 的字符串拼接，不是重新解析。
38. **L3 同类项塌缩**：连续相同动作折叠为 `（N turns）`，重复循环（如反复重试同一工具）在折叠区只占一行。
39. **流式输出合并刷新**：chat_view 按 40ms（~25fps）合并写入，把 100 tok/s 下的每秒数百次 `QTextDocument` 光标操作 + 全视口重绘压到每秒 25 次。
40. **RAG 状态缓存**：`_system_prompt()` 每轮都要注入知识库状态，原先每次同步调 `rag_engine.status()`（首次还会惰性导入 lancedb，冷启动数秒）。改为 30s TTL 缓存，同步后经 `Agent.reload_rag()` 显式失效。
41. **增量同步内容指纹**：只在「mtime+size 判为未修改」时才计算源文件字节指纹，避免每次同步对所有文件做全量哈希。
42. **解析句柄显式关闭**：docx / xlsx / pptx 解析后立即关闭底层 zip 句柄，避免 4 worker × 数千文件累积句柄。
43. **HTML 解析量上限**：`web_scan` 建 DOM 前把文本裁到 2MB（下载上限 8MB 之外再限一道解析量），避免 BeautifulSoup 建树时内存峰值放大数十倍。
44. **skill 目录 mtime 探测 TTL 缓存**：`_dir_mtime` 是 O(目录数) 的全树 walk，5 分钟扫描间隔内每次检索要 walk 一次、scan 后再 walk 一次。60s TTL 缓存把常态检索的探测成本降到 O(1)；外部写入由 `mark_stale()` 显式标脏兜底（最坏延迟 60s 被发现）。
45. **图谱向量操作列投影**：`_backfill_vectors` / `_deindex_observations` 用 `search().select([...])` 把列裁剪下推到存储层，不再把两条 768 维向量列物化进内存（与 skill_retriever / vector_store 同一修法）。
46. **UI 推理流合并刷新**：`_on_reasoning` 与正文共用 40ms 定时器与缓冲，推理模型每秒数百 chunk 的逐块全视口重绘压到 ~25fps；工具入参统一截断 400 字符，MB 级 payload 不再常驻 QTextDocument。

## 附录 B：已知约束

1. **`code_run` 超时无法强杀线程**：daemon 线程的无限循环会持续到进程退出。本地工具可接受，但生产部署需注意。
2. **MCP 工具默认 destructive**：所有 MCP 工具需用户确认，无法细粒度区分安全/危险操作。
3. **单进程单 agent**：不支持多 agent 并发对话；`Session` 是实例属性，非共享。
4. **RAG 不支持增量删除单 chunk**：`delete_by_source` 删整个 source 的所有 chunk，无法精确删除单个 chunk。
5. **摘要 LLM 调用无独立超时**：`_summarize_via_llm` 复用 `chat_stream`，依赖 LLMClient 的结构化 read 超时（每 chunk 最大间隔 60s），无更细粒度的独立控制。该路径只在兜底收缩时触发，不在常规轮次上。
6. **事实抽取 best-effort + 异步**：`_maybe_extract_facts_async` 在 daemon 线程中调用**独立的 LLMClient**（`_get_extract_llm()`，独立 `httpx.Client` 连接池），LLM 失败时静默跳过，不重试。用户关闭应用时 daemon 线程可能被强制终止（未完成的抽取会丢失）。
7. **图谱向量索引非事务**：JSON 图谱文件和 LanceDB 向量索引不是事务性写入，极端情况下（进程崩溃在两者之间）可能出现不一致。
8. **Embedding 单例不释放**：共享的 FastEmbed ONNX session 在进程退出前不 `release()`，仅由 OS 回收。这是设计选择——RAG 和图谱可能交替使用，提前释放会导致另一方崩溃。
9. **技能索引非实时**：`SkillIndex` 防抖扫描以「目录 mtime 变化」为触发条件；直接编辑已有技能目录内的 `skill.json` 内容不会改变目录 mtime，元数据变更最迟在 300s 间隔后才会被索引收录（新增/删除技能目录会立即触发）。
10. **Prompt 体积**：SYSTEM_PROMPT 精简至 ~200 tok + 动态注入（work memory 手动 scratchpad / 当天自动抽取事实 / KB 状态 / 命中技能）。长期记忆**不注入** prompt，靠 `memory_search` 工具按需检索。目录化技能的完整指令不进系统提示词，由 `skill_load` 按需读入。动态注入段**不在五级压缩的管辖范围内**（压缩只作用于 Session 的历史区），因此各有上限（事实 ≤20 条/2000 字符，技能 prompt ≤1500 字符）；抽取侧限 ≤5 实体 × 3 观察，持久化桶 ≤200 条。
11. **docling 环境约束**：docling 依赖 `pyarrow<17`，而 pyarrow 16.x 无 Python 3.13 的预编译 wheel，导致 Python 3.13 环境无法安装 docling（需 Python 3.10–3.12）。docling 未安装时系统自动回退到按格式的轻量解析器，功能不受影响，仅失去统一解析/布局理解能力。
12. **BM25 索引重建开销**：LanceDB 的 FTS 索引不会在 `add()` 后自动增量更新，每次入库后需 `replace=True` 全量重建索引。增量同步场景下重建耗时相对向量化（ONNX 嵌入）可忽略，但全量重建大知识库时会有额外开销。
13. **code_run 泄漏线程追踪上限**：超时卡死的 daemon 线程（无限循环/阻塞 I/O）无法强杀，会存活到进程退出并持有其 namespace/StringIO 引用。`_leaked_threads` 追踪列表限制最多 10 个，避免极端情况下无限增长；`_cancelled()` 协作取消机制可让协作式脚本主动退出。
14. **`skill_load` 默认入口是 `SKILL.md`**：老体系目录技能在 `skill.json` 里声明 `entry: prompt.md`，工具会在 `SKILL.md` 缺失时回退到声明的入口，再回退到 `prompt.md`。
15. **技能请求计数表有上限**：`skills.json` 的 `requests` 超过 500 条时淘汰最旧的一半，避免长期使用时文件与内存无界膨胀。
16. **共享 Embedding 单例加载失败会被重试**：`_shared_embedding_function()` 只在成功时置位，失败不缓存，网络恢复后语义切片会自动恢复（而不是本进程内永久降级到递归切片）。
17. **UI 测试需要 `pytest-qt`**：`tests/test_bridge.py`、`tests/test_integration.py`、`tests/test_ui_flow.py` 依赖 `qapp` fixture；未安装时这三个文件的用例会在 setup 阶段报 `fixture 'qapp' not found`（已加入 `pyproject.toml` 的 `test` 分组）。

18. **内核参数需按模型窗口调整**：`kernel_max_context_tokens` 默认 30k。若接的是 8k 窗口的本地模型，应显式调小，否则 RAW 区配额（40%）会远超模型实际能力；L1–L3 会照 30k 分配额度而不报错。
19. **`kernel_raw_turns` 是精度/成本权衡**：默认 2。调大 → 模型看到更多原文、更准，但 RAW 区更容易告罄、触发更频繁的 CONSOLIDATE；调小 → 更省，但长链条任务的中间步骤只留下一行摘要。
20. **流式输出仅在吸底时跟随**：用户上翻阅读/选中复制时自动跟随停止，拉回底部即恢复；吸底直接置滚动条、绝不 `setTextCursor(End)`（不覆盖用户光标与选区）。§11.21.5 曾以「作者有意设计」为由保留强制钉底，第九轮复查推翻该决定并同步更新了 `test_ui_flow` 的断言（见 §11.22.4）。
21. **docling 转换串行化**：`DocumentConverter` 未声明线程安全，转换走全局锁，4 worker 对 PDF 实际退化为单线程。详见 §11.21.5。
22. **失败自动恢复有预算上限**：反思门失败感知提醒最多 4 次、防过早 blocked 守卫最多提醒 2 次，模型坚持放弃/标记 blocked 时内核尊重其决定并在最终答复附上未完成清单——自动恢复不是无限重试。MAX_TURNS 截断与「提前收尾但计划未完成」另有自动续跑（最多 2 段，见 §11.22.1.1），额度用尽才交回用户。
22. **内核不做跨进程持久化**：`Session` 只在工作记忆 checkpoint 上落盘（`.agent/work_memory.json`），轮次历史本身随进程退出消失。重启后模型从「key_info + 图谱 + 技能」恢复，而不是从完整对话恢复。

## 12. 第十轮全量复查（安全 / 泄漏 / 正确性 / 性能 / 体验）

三个模块并行深审（RAG 1711+1338+727 行、agent 编排层 1447+970 行、工具层与 UI 16 文件 + 2173 行），按严重度修复。README「第十轮」列了完整 49 项表格，这里只记录**设计层面**的改动与新增机制。

### 12.1 风险分级的两类绕过（安全）

`tools/risk.py` 的静态启发式按「破坏性动词 + 工作区外路径」判定，旧规则漏了两类：

- **解释器内联代码**：`python3 -c "import shutil; shutil.rmtree('/Users/x')"` 不走任何 shell 动词，而 `mentions_outside_path()` 能从字符串里认出 `/Users/x`——只要动词表里有对应记号就会命中。补入 `shutil.rmtree` / `os.remove` / `os.rename` / `os.symlink` / `subprocess.run` 等 Python 侧调用名，以及 `dd` / `mkfs` / `fdisk` / `wipefs` 等磁盘级操作。`python3 script.py` 这类正常开发用法没有外部路径字面量，不会误报。
- **管道下载执行**：`_PIPE_EXEC_RE` 的目标原本只有 `(ba|z|da|fi)?sh`，`curl … | python3` / `| node` / `| perl` 完全漏网。目标扩展为 `python[\d.]*|node|perl|ruby|php`。

`code_run` 的写护栏仍是**提示性**的（只替换命名空间里的 `open`），且不能硬拦 `os.rename` / `shutil.move`——pip install 在 wheel 安装阶段就会用到它们，硬拦会让「code_run 里装包」这个既定能力回归。因此第一道防线是风险分级，写护栏只兜「忘了弹确认」的漏网情况。这一点已写进 `code_run` 的模块文档。

### 12.2 符号链接导致的任意文件读取（安全）

`skill_retriever.read_skill_dir()` 有意放行指向 skills 目录之外的符号链接（外部技能常以 `ln -s` 挂载），但无条件放行等于把 `skill_load` 变成任意文件读取：agent 可以先 `ln -s /etc <ws>/skills/x`，再 `skill_load(path="x", entry="passwd")`。注：创建该链接的 shell 命令本身会因 `ln` + 工作区外路径而弹确认，问题是用户看不出确认框里那条命令的后果。

改为**有条件放行**：链接目标必须「长得像技能目录」（顶层含 `SKILL.md` / `skill.json` / `prompt.md` 之一）。`/etc`、`/usr` 这类系统目录被直接拒绝并记 warning。读取结果若来自工作区之外，`skill_load` 会在正文前标注真实来源。

### 12.3 原子写与防抖写（资源完整性）

新增 `src/agent/atomic_io.py`，详见 §6.4.3。收敛了五处固定 `.tmp` 名的写法，并给三个 JSON store 的 `_load` 失败路径加上坏文件备份。

`GraphMemoryStore` 同时获得规模上限与防抖写：

- 每实体 observations ≤200、总实体 ≤5000、关系 ≤20000，按「最近优先」淘汰；被淘汰的条目同步从向量索引删除（新增按 observation 粒度的 `_deindex_observation`），避免「JSON 删了、向量还在」导致已删事实仍被 `search()` 召回。
- `_save()` 改为 0.5s 最小间隔的防抖写，`flush()` / `close()` / atexit 落盘。

### 12.4 自动续跑的预算放大（正确性 + 体验）

`KernelLoop.run()` 每段都会清零全部防死循环计数，而 `Agent.run` 最多自动续跑 4 段——「段内最多拦 N 次」被放大成 4×N 次，叠加每段 15 轮，单次用户输入最坏 75 轮 LLM 调用且没有墙钟上限。推理模型 20~60s/轮，表现为几十分钟不返回任何结果。

修法：`failure_snapshot()` 除原有的失败上下文外，还把 `_finish_nudge` / `_plan_finish_nudge` / `_block_nudge` / `_empty_retry` / `_reask_guard` / `_plan_nudged` 与 `_did_work` 一并导出，续跑段经 `seed_failures()` 接上。`_did_work` 跨段传递同时修掉「续跑段提醒变成『你还一次工具都没调用』」的误导文案。

`hooks.finished` 也从「每段一次」改为「整个用户轮次一次」：它内含事实抽取与 L4 蒸馏（各一次后台 LLM 调用），每段触发意味着单次输入最多 8 次冗余后台调用，并向知识图谱重复写入多条近似实体。内核 `run()` 新增 `emit_finished` 参数，`Agent.run` 在续跑循环结束后统一触发。

### 12.5 一次性提示的生命周期（正确性）

`__truncated__` / `__plan_boundary__` 原本在 `anchor_prompt()` 里 `pop` 消费。但该轮紧接着可能被反思门/前置门 rollback，提示随之消失——而自动续跑的第一轮恰恰最可能被 rollback（模型再次只给文字），于是「上一条被判提前收尾，已自动续跑」这条关键指令模型永远看不到，只能收到泛化的「还有 N 步未完成」。

改为 peek 不消费，`finish_turn()` 真正落地后才清除。回归测试 `test_one_shot_hints_survive_rollback` 覆盖「rollback 后提示仍在、提交后消失」。

### 12.6 模型缓存探测不再有下载副作用（性能）

`deps._is_embedding_model_cached()` / `_is_reranker_cached()` 原本用 `TextEmbedding(..., lazy_load=True)` 探路径。但 fastembed 部分版本的下载逻辑位于基类 `__init__` 而非 `OnnxTextEmbedding.__init__`，`lazy_load` 只跳过 ONNX Session 创建——最坏情况下「依赖检查」这一步就会在同步前的 UI 线程上开始下载 137MB / 2.3GB。

改为纯文件系统探测，覆盖两种缓存布局：

- fastembed ≥0.9 的 HuggingFace hub 风格：`models--{org}--{repo}/trees/*.json` 清单 → `blobs/<blob_id>` 内容寻址存储；
- 旧版 fastembed：`{org}/{repo}/` 直接放文件。

按清单校验每个必需文件的 blob 是否存在（排除 `.incomplete`），因此一次中断的下载（只留下 656KB 外部图）不会被误判成「已缓存」。仓库名从 fastembed 的模型名映射推导，见 §9.4 的对照表。

### 12.7 配置接线（正确性）

`rag_rerank_enabled` / `rag_rerank_model` 在 `config.py` 里定义、在 README 与本文档里宣称可用，但**没有任何代码读取它们**——`RAGEngine` 的两处构造（`tools/base.py`、`ui/main_window.py`）都不传 `rerank_model`。现已透传；关闭时 `search()` 直接走混合检索排序，且不会加载 ~2.3GB 的 reranker 权重。

`Agent.max_iterations` 从 `__init__` 快照改成 property（读实时取 `config`，写也落 `config`），修掉「UI 改了最大轮次却没反应」。

### 12.8 reranker 归一化的语义稳定性（正确性）

旧实现用 `any(abs(s) > 1.0)` 决定是否对**本批候选**做 sigmoid：同一个 chunk 在不同查询下可能走/不走归一化，绝对值之间不可比，而 `min_similarity=0.7` 是绝对语义的阈值——阈值语义会随查询漂移。另外 `1/(1+exp(-s))` 在 `s` 为很大负数时 `OverflowError`，被外层 except 吞掉后静默回退到向量排序，精排看起来「生效」了其实一次都没用。

改为首次打分时探测一次输出范围并**按模型固定**缓存结论；sigmoid 用数值稳定分支写法（两个方向都只算一次 `exp`）。

### 12.9 其余修复

- `VectorStore.close()` 补复位 `_documents_table`（LanceDB table 持有打开时的版本快照，只置空 `_table/_db` 会让复活的实例继续往旧连接上写）；删掉对 ONNX reranker 调 `cpu()` 的死代码。

## 13. 第十一轮全量复查（正确性 / 泄漏 / 进程稳定性）

对全部 45 个源文件（~30k 行）做了逐文件重审。本轮最重要的发现是 **code_run
泄漏线程「自杀机制」整体失效**——它由两个独立缺陷叠加构成，最终表现为
pytest 进程退出时 `Fatal Python error: _enter_buffered_busy`（持 stdout 缓冲锁
abort，exit=134）；生产 GUI 下则是一直往真实 stdout 刷屏的失控线程。

### 13.1 `_BoundedIO` 截断快速路径绕过 closed 检查（根因 A）

`code_run` 的超时/取消收尾依赖「close 缓冲 → 泄漏线程下一次 `print` 撞
`ValueError: I/O operation on closed file` → 线程自行退出」。但
`_BoundedIO.write` 的截断快速路径（`_truncated → return 0`）**先于**
`io.StringIO.write` 的 closed 检查执行——死循环脚本在超时前早已把缓冲写满
（上限 200K 字符），此后所有 write 都走快速路径返回 0，`close()` 对它们
**完全不生效**。泄漏线程因此永不退出。

修复：`write` 显式检查 `self.closed`（在任何快速路径之前抛 `ValueError`）。

### 13.2 全局 stdout 的恢复时序（根因 B）

即便 write 修复，旧恢复顺序（先 `sys.stdout = 真实流` 再 `close 缓冲`）仍让
泄漏线程的 `print`（每次动态查找 `sys.stdout`）拿到**真实流**——永远碰不到
已关闭的缓冲。修复后时序：

- **正常完成**（worker 已 join）：立即恢复全局流，与旧行为一致；
- **超时/取消**（泄漏线程仍在跑）：先 close 缓冲，全局流**保持**指向已关闭
  缓冲 50ms（`_LEAK_RESTORE_DELAY`），泄漏线程的下一次 `print` 即撞
  `ValueError` 自行退出，随后由后台线程恢复全局流。

配套新增模块级「真实流」缓存（`_snapshot_real_streams`）：50ms 恢复窗口内
若紧接着启动下一场 code_run，它快照到的 `_prev_stdout` 会是上一场**已关闭**
的缓冲——直接恢复回去会把全局 stdout 永久钉死在死流上。快照函数识别这种
stale 状态并沿用模块级缓存的真实流；延迟恢复线程只在全局流仍指向**本场**
缓冲时才动手（不覆盖后续场次）。

### 13.3 ingest 收尾崩溃：`stats["errors"]` 被覆盖成 int

`engine._chunk_iter` 处理「文件在扫描后不可读」时写的是
`stats["errors"] = stats.get("errors", 0) + 1`——而 `errors` 在 stats 里是**列表**
（其余所有错误路径都 `append`）。一次文件消失抖动就会让它变成 int，同步收尾
的 `len(stats["errors"])` 随即 `TypeError`：整轮**已经成功**的同步以异常告终
（UI 显示「显示结果时出错」）。同时该写法不持 `stats_lock`，与 worker 线程的
append 并发。修复：持锁 `append` 一条错误记录，与其他路径同构。

### 13.4 WorkMemory LRU 缓存的锁外变更

`_work_memory` 的缓存是 `OrderedDict`，`move_to_end`（最近使用）写在锁外，
与锁内淘汰路径的 `popitem(last=False)` 并发修改 → `RuntimeError` / 条目错乱。
`move_to_end` 移入 `_work_memory_lock` 内，命中/新建/淘汰三者同锁。

### 13.5 code_run 护栏对非路径参数的误导性错误

`open(1.5, 'w')` 这类调用：旧护栏对非 `str/PathLike` 的 `file` 走
`realpath("")`——返回 **cwd（= workspace）**，前缀检查通过，随后
`_real_open` 抛出与根因无关的底层 `TypeError`，模型无法据此修正。现在直接
报 `open() expects a path (str/PathLike), got float`。

### 13.6 UI 配置钳制

`request_timeout ≤ 0` 会让 httpx 立即超时（所有请求必失败）、`temperature < 0`
被多数 API 拒绝——两者此前都不校验。现在钳到合法下限并复位输入框，与既有
的非法值回退提示共用状态栏通道。

### 13.7 回归测试

`tests/test_full_review_fixes.py`（5 例）：ingest errors 保持列表（模拟文件在
扫描后消失）、WorkMemory LRU 48 线程并发命中/淘汰、护栏拒绝非路径 open、
code_run 超时后泄漏线程 3s 内自行退出且全局流恢复（直接回归 §13.1/13.2 的
Fatal abort）。`test_code_run_leaked_thread_does_not_hijack_stdout` 的
`real_stdout` 记录时机同步修正（超时返回后立即读取会撞上 50ms 恢复窗口）。

## 14. 第十二轮全量复查（OCR 失效 / 竞态 / 加载校验 / 性能）

本轮再次对全部源码逐文件重审：两个子代理并行审查「技能 + 记忆」与「RAG 解析 +
切片」两个子系统，主代理审查内核 / UI / 工具层。结论是代码库整体质量很高（前十一
轮的修复都站住了），但发现 **OCR 功能在两个层面上从未真正工作**，以及一批并发 /
加载校验 / 性能问题。

### 14.1 OCR 在 rapidocr 1.2.x 上完全失效（根因 A：模块布局）

`ocr_engine._ort_infer_session_class()` 的候选模块清单写的是
`rapidocr_onnxruntime.utils.infer_engine` 等子模块路径，并且要求类上有
`_get_ep_list` 方法。而 rapidocr-onnxruntime 1.2.x（当前最新版）的真实布局是顶层
`rapidocr_onnxruntime.utils`，且 EP 列表在 `OrtInferSession.__init__` 里内联构建，
**没有** `_get_ep_list`。两个条件同时不满足 → 函数永远返回 None →
`create_ocr_engine` 打一条「找不到 OrtInferSession」的 warning 后静默回退 CPU EP。
Apple Silicon 上的 CoreML 加速（CPU+GPU+ANE）自此功能上线起从未生效。

修复：候选清单补 1.2.x 布局；类发现只要求「模块里有 OrtInferSession」；新增
**factory 注入路径**——包装 `OrtInferSession` 所在模块的 `InferenceSession` 全局
引用，在其 `providers` 参数里注入 `CoreMLExecutionProvider`（`MLComputeUnits=ALL`），
语义与包装 `_get_ep_list` 的旧路径一致（CoreML 排最前、CPU 保留作回退，ORT 自动
把不支持的子图降级到 CPU）。`_unpatch_coreml_ep` 两条路径都能恢复。非 rapidocr
模块的类拒绝 patch（避免误伤无关代码）。

### 14.2 OCR 引擎构造 100% 失败（根因 B：上游 kwargs 缺陷）

rapidocr 1.2.x 的 `UpdateParameters.update_det_params` 在收到**任何** `det_*`
kwargs 时都无条件读 `det_dict['model_path']`。我们传 `det_limit_side_len=1024`
（提升小字识别的分辨率调优）而不传 `det_model_path`，直接抛
`KeyError: 'model_path'`——引擎根本建不起来。异常被 `_get_ocr_engine` 的兜底
`except Exception` 吞掉后返回 None，用户侧看到的是「RapidOCR 未安装，请
pip install」的误导性提示（实际已安装）。

修复：`_build_rapid_ocr` 降级链——① 完整 kwargs；② 补 `det_model_path=""`
（空值让上游回退到自带模型路径）；③ 裸构造（放弃调优保可用）。任一成功即返回；
非兼容性异常（模型下载失败等）直接上抛，重试无意义。

### 14.3 技能检索的懒初始化竞态与 sync 原子性

`SkillVectorStore._get_ef/_get_db/_get_table` 三个 getter 完全无锁：
`_get_db` 的 check-then-act 会让两个并发首次调用各建一个 `lancedb.connect()`，
后写者覆盖 `_db`，先建的连接（含文件句柄）永不关闭；`_table` 同理。修复为双检锁，
`_lock` 同步改为 RLock（`build()/sync()` 持锁期间会调用这些 getter，普通 Lock 会
自锁死）。

`sync()` 在取锁**前**读取表，且更新项「先 delete 再 add」：前者与并发
build/close 交错时会拿到已 drop 的表句柄；后者在 embedding/add 失败时让该技能从
索引里永久消失且无回滚。修复：锁内重新取表（表被清掉则锁内重建）；更新项改
「先 add 新行、再按**旧 fingerprint** 精确删除」（不能按 dir 删——那会把刚 add
的新行一起删掉）。失败窗口的最坏结果是短暂重复行，而检索按 dir 字典合并，重复行
无害。

### 14.4 技能链的加载校验

- `graph_memory._load` 对 relations 完全不校验、entities 值不校验、根节点不校验：
  只要能解析的 JSON（手改坏 / 旧版本 / 写一半崩溃）就会让 `_prune_locked` /
  `snapshot` / `list_relations` 抛异常，把**整个记忆系统**打炸。现在统一归一化：
  非 dict 根按空处理；实体值必须 dict 且 observations 必须 list；关系必须
  source/target/label 齐全，其余跳过。
- `skill_index._read_skill_meta` 只捕 `OSError/JSONDecodeError`：`name` 是数字时
  `.strip()` 抛 AttributeError、`keywords` 是字符串时列表推导抛 TypeError，一个
  手写坏的 skill.json 让整次 scan/search 失败。现在逐字段 isinstance 校验，异常面
  补 `TypeError/AttributeError`；`os.scandir` 本身也包 try（目录权限变化不再让
  `__init__` 失败）；`_load` 过滤非 dict 记录；`list_all` 返回拷贝（浅拷贝会让
  调用方污染索引）；同分排序加 name 次级键（`os.scandir` 顺序不稳定会让两次查询
  返回不同顺序）。
- `_parse_frontmatter` 要求 `text.startswith("---")`：Windows 编辑器保存的
  SKILL.md 必带 UTF-8 BOM，frontmatter 整体不可见 → 技能被静默丢弃。现在先
  `lstrip("\ufeff \t\r\n")`。
- `SkillVectorStore._distance_to_similarity(None)` 旧实现按距离 0 算成满分 1.0：
  任何缺 `_distance` 的行都必过 0.5 阈值并排到最前，排序失效。None/非数字返回
  0.0。

### 14.5 skills.py 的持久化健壮性

`skill.json` / `prompt.md` 从裸 `open()+write()` 改为 `atomic_write_text`
（唯一临时名 + fsync + replace，崩溃不留半截文件——半截 skill.json 会让
SkillIndex 静默跳过该技能）；目录唯一性从 `while os.path.exists`（TOCTOU，两个
线程同名技能互相覆盖）改为 `makedirs(exist_ok=False)` + `FileExistsError` 重试；
`create_skill/create_dir_skill` 入口处容忍 `keywords=None`；
`SkillManager.__init__` 的损坏修复现在真正落盘。

**本轮修复自身引入并被回归测试抓住的回归**：修复落盘用的
`flush(force=True)` 会把 `_JsonStore._last_save` 刷成当前时刻，紧接着第一次
`set()` 被 0.5s 防抖吞掉——表现为「刚创建的技能换个实例读不到」
（`test_skills_persist` 立即抓到）。修复：强制 flush 后复位 `_last_save = 0.0`，
保持「首次真实写入立即落盘」的旧语义，并新增
`test_repair_does_not_swallow_next_write` 锁定该行为。

`_request_key` 旧实现把长 key 截断到 80 字符：两个只有尾部不同的长请求碰撞成同一
计数键，产生虚假的「重复请求 → 建议固化」。现在超长 key 补全文 sha1 后缀，短 key
格式不变（兼容磁盘上已有的计数）。

### 14.6 安全 / 解析 / 性能杂项

- `risk._SHELL_REDIRECT_RE` 旧实现只匹配 `>/`：`> ~/.bashrc` 与 `>> ../outside`
  两种工作区外写入零确认执行。放宽为 `>>?\s*(?:~|\.\./|/)`（`./` 仍不算风险）；
  路径 token 的尾部标点剥离补 `!?]>`。
- `MCPClient.start()` 不清理上一次连接的残留：`_fail_pending`（瞬时写失败）把
  `_running` 永久置 False 后，重启时旧写队列里的 `None` 哨兵被新写线程立刻消费并
  退出 → 之后所有 `_call` 干等 30~300s 超时；卡在 `get()` 里的旧 writer 还会把
  新连接再次判死。修复：`start()` 先排空写队列 + 清 `_pending/_results`；
  `stop()` 换全新写队列，把卡死的旧 writer 隔离在旧队列上（daemon，无害）。
- `MCPTool` 把模型多传的未声明参数原样转发给严格校验的 server → 直接失败且错误
  指向远端。现在按 schema properties 过滤（properties 为空时不过滤）；MCP 重名
  工具被跳过时记 warning（此前静默吞掉，用户以为两个 server 的工具都挂了）。
- `document_outline._HEADING_RE` 的 `\s+` 匹配换行：`#\n标题` 这种空 ATX 标题行
  把下一行正文吞并成章节标题。改 `[ \t]+`。
- `cleaner` 的字母比例统计从逐字符 `isalnum()/isspace()`（纯解释器级 O(n)）改为
  预编译正则 C 层计数；语义等价（`\w` ≈ isalnum，纯分隔行仍被分隔符规则收掉）。
- `parsers._extract_pdf` 信号量内的「双重检查」是死代码（局部变量其它 worker 改
  不到），删除；`ebook-convert` 返回码 0 但输出为空时不再静默跳过 raw 回退路径；
  `_get_ocr_engine` 对持续初始化失败加 60s 负缓存冷却（模型下载失败时不再每个
  图片型 PDF 重试一遍完整加载），`release_ocr_engine` 同步清冷却。

## 15. 第十三轮：RAG 主线同步（向量库 / OCR / 切片 / 调度）

两侧工程自 #88 起分叉：本工程在 agent/内核/UI/技能/MCP 方向继续演进，Base-Aug-Agent
主线则专注 RAG，累计约 130 个提交。本轮将主线 RAG 的最新实现完整移植进本工程，
保持两边 RAG 部分状态一致。主线自身已修掉的一次性诊断脚本、线程数自适应的实时
阶段等一次性/环境相关项不收，其余全部对齐。

### 15.1 向量库：在途操作计数与生命周期

**在途操作计数（`_begin_op`/`_end_op`/`_drain_ops`/`_resume_ops`）**：`clear()`
会 `drop_table`、`close()` 会把 `_db` 置 None，二者与在途的 `add`/`search` 并发
时，在途操作会打到已删除的表或 None 连接上（表现为随机 AttributeError，或检索到
已删除的数据）。现在 16 个公开方法统一挂 `@_store_op`，`clear`/`close`/`reload`
先 `_drain_ops()` 排空再动手。`close()` 排空后**不恢复**（close 后本应永久拒绝新
操作），`clear`/`reload` 在 `finally` 里 `_resume_ops()`。

注意两个坑：① `clear()` 自身**不能**加 `@_store_op`——它会先把自己登记成在途
操作，随后 `_drain_ops()` 就等自己结束（自锁）；② flock 绑定在 open file
description 上，同线程同文件再 open 得到的 fd 与已有 `LOCK_EX` 互斥，因此
manifest 锁在进程内用普通 `threading.Lock` + 线程本地重入计数（TLS depth）解耦，
嵌套进入只加计数不再 flock。

**close 的语义差异**：主线的 close 是永久的（`_ensure_initialized` 见到
`_closed` 直接抛），而本工程的实例支持 close 后复活重连（`_initialize_locked`
复位 `_closed`）。保留本工程语义，但复活时必须**同时复位 `_closing`**——close 的
`_drain_ops()` 会把它置 True 且不再复位，不复位会让复活后的实例被 `_begin_op`
永久拒绝。

**FTS 失败闩锁**：`_ensure_fts_index` 失败后置 `_fts_failed=True`。旧实现只置
`_fts_checked`，而该标志全项目没有任何读取点——于是每次检索都重跑一遍昂贵的全库
建索引然后再次失败。`ImportError` 必须单独捕获：0.25.x 上没有 `lancedb.index.FTS`
这个模块，若掉进通用 except 分支，`_fts_failed` 置 True 后 0.25.x 的回退路径
（`create_fts_index(use_tantivy=False)`）就永远走不到，BM25 永久禁用。

### 15.2 向量库：混合检索的分数语义与 prefilter

`search_fts` 的 `_score` 是 Tantivy/原生 FTS 的原始 BM25 分（无上界，常见 5~30+）。
旧实现把它直接塞进 `score` 字段，而 `score` 在有向量候选的场合被当作 [0,1] 余弦
相似度使用，`_rerank_fallback` 会对其做 `1 - s²/2` 换算——BM25=15 会被算成
1-112.5 → clamp 到 0.0，纯关键词候选集体排到末尾，reranker 不可用时混合检索静默
退化成纯向量检索。现在 `score = s/(1+s)` 归一化，原始分另存 `fts_score`。

`search` 的 `where` 加 `prefilter=True`：默认后置过滤是「先取 ANN top-k 再过滤」，
定向检索（`rag_search(source=...)`）下候选会被先截断再筛，可能漏召回甚至返回空。

reranker 状态机两处竞态修复：`_get_reranker` 对 close 后的实例直接返回 None
（后台线程看到 `_closed` 会把状态置 `failed`，旧实现直接 return 让状态永久卡在
`loading` → 之后所有 rerank() 命中 loading 分支返回 None，重排静默失效且无日志）；
状态转换从「读到 idle」到「写入 loading」之间加锁（两个并发调用方都会各自起一个
加载线程，各加载一份 ~2.3GB 模型，后写者覆盖前者，先建的那份成为纯泄漏）。

### 15.3 向量库：嵌入的排序分桶与自适应子批

`_embed_chunks` 重写：

1. **按文本长度降序分桶**（#122）：fastembed 的批内所有序列 padding 到批内最长，
   长度混杂的批 padding 浪费 2-4 倍算力。实测 32 条混杂批 309s ≈ 40 tok/s，而同
   模型「长度排序 + 8-12 条/批」可达 ~2000 tok/s，差 30 倍。排序后每批长度相近、
   padding 归零，向量按原顺序回填，结果与混杂批完全一致。
2. **自适应子批 1-5**（#125，#126/#127/#128 生产验证修订）：真实切片上吞吐与内存
   都随子批增大单调变差，size2 双优。调优器按实测速率在边界上收敛（最后 3 次观测
   一致才收），下边界只需一次成功子批，上界每档都需成功证据。
3. **激活形状预算**（#126 修订）：每个子批组装时按 `_shape_cap_size` 钳制条数
   （激活 ∝ 条数 × 批内最长序列²），超长文本自动变小，把瞬时激活压在 ~2GB。
4. **RSS 软墙 8GB**（#129）：真实同步进程基线 6-10GB，绝对阈值会误触发；超墙只
   要求降档避让，回墙下即停，**无闩锁**（旧 5GB 闩锁版是「卡死在 1」的根因），
   恢复交给调优器自身的恢复分支/重爬。
5. **子批级进度日志**：嵌入一个子批要数十秒且中间完全静默，用户会误判为卡死。

### 15.4 OCR：3.x 优先、暗色反色、周期回收

**引擎选择**：`_build_ocr_engine` 优先 rapidocr 3.x（模型目录与 docling 共享、
懒加载、支持 CoreML EP），未安装再回退 1.x（经 `ocr_engine` 注入 CoreML EP）。
Apple Silicon 上 3.x 传 `params={"EngineConfig.onnxruntime.use_coreml": True}`；
**Intel/非 Apple 平台直接不传**——rapidocr 的 `is_coreml_available()` 仅在
arm64 上为真，x86_64 上必然走 CoreML 初始化失败分支。CoreML 初始化失败自动回退
CPU EP。构造后预热一次（空图）：模型本来马上就会被用到，预热同时消除首页 OCR 的
加载延迟并探测实际生效的 EP。Apple 检测复用 `ocr_engine.is_apple_silicon`
（sysctl 读真实 CPU 型号，Rosetta 下 `platform.machine()` 会谎报 x86_64）。

**暗色主题反色**（#100-#101）：RapidOCR 的 det/rec 模型在白底黑字、高对比度样本
上训练，黑底白字/灰字的暗色主题页几乎检不出任何文本框——「一大片页面检测不到
文字」的根因。页面整体偏暗（p50 < 100 且 p95 < 160）时反色为白底深字；插图占比
大的正常页 p95 远超 160，不会误触发。反色后进 CLAHE（局部对比度增强同时覆盖低
对比度拉伸，与主线的两步分位数拉伸等价）。

**`_pixmap_is_blank`**：均匀采样至多 8192 字节取 min/max，极差 ≤ 12 视为近纯色
（覆盖纯色占位图与扫描件的空白纸页）。这些页送 OCR 必然返回 "text detection
result is empty"，每页白耗 2-5 秒。

**引擎周期回收 + 每页取用**（#119/#123/#130）：CoreML/ORT 的原生缓存按输入形状
保留，真实扫描页约 35MB/页——400 页扫描书滞留 ~14GB，进程退出前不释放。每 50 页
强制重建引擎冲刷缓存（系统扫描 N=10..100 证实热重建仅 1-2s/次、峰值足迹各 N 下
持平 ~5.2GB）。**关键**：回收必须配合「每页从进程级单例取用、页末释放局部引用」，
否则周期回收只影响触发回收的那个 worker，其它 worker 仍抱着旧引擎继续用——最多
4 代引擎的原生缓存并存，回收形同虚设。每页取用后任意时刻至多一代引擎存活。
单页 OCR 后 `store_shrink(100)` + `gc.collect()` 回收 MuPDF store 里缓存的解码图。

**输出格式兼容**：3.x 返回 `RapidOCROutput`（行文本在 `.txts`），1.x 返回
`(result, elapse)`（`[box, text, score]` 列表），`_ocr_image_cached` 两者都支持。

### 15.5 ingest 调度：LPT 分片与批量写入

`_shard_files_balanced` 按文件大小降序 + 贪心最轻负载分配：最大的 N 个文件必然
分属不同 worker，n ≥ workers 时空片不可能出现（旧连续切片在 9 文件 4 worker 时
第 4 片为空），慢书（按页 OCR）自动摊开，尾延迟显著缩短。

写入批量 20 → 200：LanceDB 每次 `add` 都产生一个新 fragment，批 20 在大库上留下
海量碎片，检索退化为逐段扫描。`stats["chunks"]` 从「全库总数」改为「本次写入量」
（UI 用它展示「本次新增多少切片」），并新增 `stats["chunks_total"]`。

### 15.6 同步一致性：manifest 锁与合并

`_ManifestLock`（fcntl.flock 跨进程 + 线程锁 + TLS 重入计数）与
`_save_manifest` 的读改写合并：UI 的 SyncKnowledgeWorker 与 agent 的 rag_ingest
各持一个 RAGEngine 实例、各一份内存 manifest 快照，旧实现的全量覆盖写会让后写者
抹掉前者刚写入的条目——「已同步」的文件被判为「未同步」，下次全量重跑。
`removed` 参数区分「本次有意删除」与「别的实例刚写入」，否则删除会被合并逻辑复活。
`clear_knowledge_base` 删 manifest 也持锁（否则并发的实例一个 `os.replace` 就把
manifest 复活 → 向量库空、记录满，此后所有文件都被判「已同步」而跳过）。

**Markdown sidecar**（`*.md.meta.json`）：缓存文件名经过 `_safe_filename` 清洗
（空格、括号、中文标点被丢、截断到 32 字符），从文件名反推 doc_name 必然失真
（"Report 2024.pdf" → "Report2024.pdf"），导致每轮同步都查不到已有记录 → 全文
重读 + 重建 digest + 用错名字再写一条 → documents 表永久重复条目。sidecar 记录
「缓存文件名 → 原始 source 相对路径」，`ensure_digests` 按 sidecar → 表记录按
md_path 反查 → 文件名反推的优先级解析。`build_and_store_digest` 支持传入预计算的
digest/chapters（批量重刷不再算两遍）并存完整 doc_name（相对路径，basename 会让
不同目录的同名文件共用 doc_id 互相覆盖）。

### 15.7 清理路径的健壮性

`_cleanup_deleted_files` 逐文件 try/except 隔离：单个文件删除失败不能中断整个清理
（此时向量写入已完成、manifest 尚未保存，一次 LanceDB 异常带着未保存的 manifest
崩溃退出会让增量同步状态不一致）。失败的文件**保留在 manifest 里**，下次同步重试
——旧实现无条件 `pop`，「下次重试」的承诺永远不成立（条目已不在 manifest，
`_cleanup_deleted_files` 只遍历 manifest 键），失败文件的向量永久残留且仍可被
检索。为此 `delete_by_source` 的返回值语义从「失败返回 0」改为「失败上抛」。
删除范围补齐：`delete_document` 按 rel_path / basename / 完整路径三个键都删
（doc_name 存的是相对路径，其 doc_id 是 md 缓存路径的哈希——只按 basename 找永远
找不到子目录文件的行，digest 孤儿行永久累积，rag_outline 继续列出已删文档），
sidecar 一并清掉。

### 15.8 解析与依赖

旧版二进制格式（`.doc`/`.xls`/`.ppt`）移出 `SUPPORTED_EXTENSIONS` 与
`EXTENSION_DEPS`：python-docx/openpyxl/python-pptx 与 docling 均只支持 OOXML，
解析必然失败，保留在支持列表里只会让用户误以为可用；直接调用 `extract_text`
时给出「另存为 .docx/.xlsx/.pptx」的可行动提示。OCR 引擎从 `EXTENSION_DEPS` 的
静态项改为 `check_dependencies` 检测到图片版 PDF 时**动态升级**为必需依赖
（#111：「未装 OCR」与「装了但加载失败」在依赖层无法区分，统一 optional 会让两者
都只产出无差别的「可选缺失」提示）。pyproject 的 ocr extra 改 `rapidocr>=3.10`、
rag extra 加 `model2vec>=0.3`（语义切片快路径）。

## 16. 嵌入模型：量化版与 CPU-only 的显式强制

用户要求确认两点：nomic-embed-text 用的是量化版，且 CPU-only 是被**强制**的。
核查结论：量化版一直成立，但 CPU-only 此前只是 FastEmbed 的默认回退，并非保证。
本轮把两点都固化为显式行为并加回归测试。

### 16.1 量化版（已成立，本次加固测试）

默认模型名 `nomic-ai/nomic-embed-text-v1.5-Q`，在 FastEmbed 0.9.0 的注册表里
映射到 `onnx/model_quantized.onnx`（int8，~137MB，768 维），而非 fp32 的
`onnx/model.onnx（~548MB）。本地缓存实测加载路径为
`model_quantized.onnx`，文件 131MB。`AgentConfig` 还会把显式写成非量化名的
配置迁移到 `-Q`（`test_config.py::test_migrate_nonquantized_to_quantized` 覆盖）。

### 16.2 CPU-only：从「默认回退」到「显式强制」

FastEmbed 的 EP 选择逻辑（`fastembed/common/onnx_model.py`）：

```python
if providers is not None:
    onnx_providers = list(providers)
elif explicit_cuda or (cuda == Device.AUTO and cuda_available):
    onnx_providers = ["CUDAExecutionProvider"]
else:
    onnx_providers = ["CPUExecutionProvider"]
```

`cuda_available = "CUDAExecutionProvider" in available_providers`。本机
（Intel Mac + onnxruntime 1.23.2）可用 provider 列表是
`['CoreMLExecutionProvider', 'AzureExecutionProvider', 'CPUExecutionProvider']`，
不含 CUDA，因此实际落到 CPU——但这只是**该环境的巧合**，不是代码的保证：
任何装了 `onnxruntime-gpu` 的环境都会静默切到 CUDA。

后果不只是「用了 GPU」：嵌入是 RAG 的数值地基，GPU/CPU 的算子实现与归约顺序
不同会让向量有细微差异，而向量库是持久化的——同一库在不同机器上混用两种 EP
检索，相似度排序可能出现难以复现的漂移。此外本项目 OCR（RapidOCR）、解析、
reranker 全程 CPU，嵌入单独跑 GPU 还会引入 GPU 显存与 OCR/解析争抢的问题。

因此 `FastEmbedEmbeddingFunction._ensure_model` 与 reranker 的
`TextCrossEncoder` 构造都显式传 `providers=["CPUExecutionProvider"]`。

**版本兼容**：`providers` 参数在较老的 fastembed 上不存在（poetry.lock 仍锁
0.8.0，而 pyproject 已要求 `>=0.9.0`）。用 `_cpu_only_kwargs(cls)` 做签名探测
而非 try/except TypeError——加载失败的原因很多（模型下载失败、缓存权限…），
把「参数不支持」和「模型下载失败」混进同一个异常分支会让错误信息误导用户。
探测不到就退化为不传（旧版本行为不变）。

### 16.3 回归测试

`tests/test_embedding_cpu_only.py`（7 例）：默认模型名是 `-Q` 量化版；
FastEmbed 注册表里 `-Q` 映射到 `model_quantized.onnx` 且体积不足 fp32 一半；
config 迁移非量化名；`_cpu_only_kwargs` 对 `TextEmbedding` / `TextCrossEncoder`
返回 CPU-only 参数、对签名不支持的类返回 `{}`；驱动 `_ensure_model` 验证构造
时确实传了 `providers` 且没有把 `cuda` 留在 AUTO。

全量 626 个用例通过。

### 16.4 重排序模型：同样的两个问题，其中一个曾是真 bug

用户接着要求确认 reranker（bge-reranker-v2-m3）也是量化版 + CPU-only。核查结果：

**量化版——此前不成立（真 bug）**。FastEmbed 的 reranker 注册表里有两个变体：

| FastEmbed 模型名 | ONNX 文件 | 体积 |
|---|---|---|
| `BAAI/bge-reranker-v2-m3` | `onnx/model.onnx`（fp32） | 2.27GB |
| `BAAI/bge-reranker-v2-m3-int8` | `onnx/model_int8.onnx`（int8） | 0.57GB |

代码里的意图一直是 int8——`vector_store.DEFAULT_RERANK_MODEL`、
`deps.RERANK_MODEL_ID`、`deps._RERANK_REQUIRED_FILES`（探测
`onnx/model_int8.onnx`）三处都是 int8。但**运行时的四个默认值站点全是 fp32
名**：`config.rag_rerank_model`、`RAGEngine.__init__ 的 rerank_model`、
`tools/base.py` 的 getattr 兜底、`ui/main_window.py` 的 getattr 兜底。
`DEFAULT_RERANK_MODEL` 因此是死代码——每个真实调用方都显式传了模型名。

后果不只是「用了 fp32」：deps 的预下载与缓存探测按 int8 走（用户看到
「重排序模型已缓存 ✓」），运行时却按 fp32 名加载——首次检索会**再触发一次
2.27GB 的意外下载**，预下载的 570MB 白下；常驻内存也是 4 倍。本机缓存里
`model.onnx` 只有 644K（一次中断的残缺下载）而 `model_int8.onnx` 是完整的
544M，正是这个分裂的现场证据。

修复：四个站点全部改为 int8，并统一从 `vector_store.DEFAULT_RERANK_MODEL`
取值（engine 本就 import 它，另两处补 import），消除「意图值分散在五处」的
漂移空间。`config._migrate()` 增加 fp32 → int8 的迁移——旧配置里持久化的
fp32 名必须迁走，否则老用户继续每次加载 2.27GB（与嵌入模型的非量化名迁移
同一套路）。用户显式选择的其它 reranker（如 `bge-reranker-base`）不迁移。

**CPU-only——本轮已加固**。`vector_store._get_reranker` 的 TextCrossEncoder
构造显式传 `providers=["CPUExecutionProvider"]`（经 `_cpu_only_kwargs` 签名
探测，兼容老版 fastembed）；`deps._download_reranker_model` 的探测构造也补上
（`lazy_load=True` 本就不建 onnx 会话，属防御性）。

**质量验证**：int8 只输出排序分数，量化对排序质量的影响可忽略。实测
（query=「向量数据库 相似度检索」）：两篇相关文档 6.34 / -3.25，无关文档
-11.02，分离度清晰。ONNX int8 在 CPU EP 上还比 fp32 更快。
